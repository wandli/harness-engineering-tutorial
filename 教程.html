这份教程是什么，给谁看

Harness 工程（Harness Engineering）是 2026 年初才被叫出名字、但从 2024 年起就在实践的一门手艺：模型之外的一切，决定了一个 AI Agent 到底能不能把活干完。本教程假设你会写一点 Python、用过 ChatGPT 或 Claude 这类聊天产品，但从没自己写过 agent。读完并做完练习，你会：

  1. 说清楚 harness 是什么、和 prompt engineering / context engineering 的关系、为什么 2026 年所有人都在谈它。
  2. 亲手写一个 200 行左右的 coding agent harness 并跑起来。
  3. 知道 Claude Code、Codex CLI 这类产品里的每个功能分别在解决哪一类 harness 问题。
  4. 掌握评测和迭代 harness 的方法，也就是这门手艺的日常。

配套文件在同一目录：mini_harness.py（完整可运行的最小 harness）、mini_eval.py（评测脚本）、tasks/fix_add/（一个示例任务，含起始仓库、任务描述和 grader）。资料截至 2026 年 10 月，关键结论都给了出处，文末有阅读清单。

阅读路线：第 0 课讲概念；第 1 到 7 课边学边写代码，每课对应 mini_harness.py 里的一段；第 8 到 10 课讲进阶模式、日常工具对照和心法。只想动手的可以直接从第 1 课开始，回头再补第 0 课。

第 0 课先把名字搞清楚：什么是 Harness

词源与比喻。Harness 原意是马具：缰绳、马鞍、嚼子。中文圈的说法是"Agent 是牛马，Harness 是缰绳"。它和汽车行业的"线束（wire harness）"没有任何关系，搜中文资料时别被带偏。中文媒体一般直接写"Harness 工程"，偶尔意译为"脚手架"或"运行框架"。

一句话定义。Agent = Model + Harness。模型负责思考，harness 是模型之外的一切：调用模型的那个循环、它能用的工具、系统提示词和项目说明文件、上下文怎么增删、权限和沙箱、记忆和状态、怎么判断做完了。Anthropic 官方文档的说法是"围绕模型、提供工具并管理模型所见上下文的那一层"；Thoughtworks 的 Birgitta Böckeler 说得更直白："AI agent 里除了模型之外的一切"；LangChain 的口号是 "If you're not the model, you're the harness"。

实际使用中这个词有三个粒度，读文章时要分清：

  • 窄义，运行时：调模型、分发工具调用、决定何时停的那段代码（Hugging Face 术语表、arXiv 2609.00006 对 11 个开源 harness 的源码研究用这个意思）。
  • 广义，模型之外的一切（Böckeler、Addy Osmani、LangChain）。
  • 仓库级：OpenAI 那篇博客的用法，harness 还包括代码仓库自身的文档结构、自定义 linter、结构化测试、可观测性，也就是 agent "生活"的整个环境。

还有一个容易混淆的点：Terminal-Bench 排行榜的 "agent" 列（Claude Code、Codex CLI、Terminus 2）就是别处说的 harness，而它自己说的 "harness"（Harbor）指评测框架。

Hashimoto 给的定义最适合初学者记住：每次发现 agent 犯了一个错，就做一个工程化的方案，让它永远不再犯同样的错。方案只有两种形式：更好的隐式提示（AGENTS.md 之类），或者真正写出来的工具。

和 prompt engineering、context engineering 的关系。多数 2026 年的文章把三者嵌套：

  • Prompt engineering：怎么措辞。作用对象是一次交互里的文字。
  • Context engineering：每一步模型窗口里到底放哪些 token（系统提示、工具定义、历史、检索结果、笔记）。
  • Harness engineering：产生这些 token 的代码本身，再加上循环、工具、权限、状态、验证。

Osmani 的说法是"harness 主要是 context engineering 的投递机制"。Böckeler 反过来把 harness 工程放在 context engineering 之内，属少数用法。Karpathy 2026 年提的 "agentic engineering" 指人类通过 agent 做工程这件事本身，harness 工程是其中一项技能。

为什么值得学：证据。同一个模型、换一个 harness，分数差别可以很大：

也要知道反方。几件事同样有证据：

  • 好 harness 之间差距不大。ICML 2026 的 "Scaffold Effect" 研究：同一模型在 Goose / OpenCode / OpenHands 之间通过率差 0 到 8 个百分点，但消耗的 token 相差最多 40 倍。Terminal-Bench 2.0 作者的结论是"模型选择通常比 scaffold 更重要"。
  • 强模型需要的 harness 更少。约 100 行 Python、只有 bash 一个工具的 mini-SWE-agent 在 SWE-bench Verified 上超过 74%；在 Terminal-Bench 2.0 上用 Sonnet 4.5 得 42.5%，和同模型的 Claude Code（40.1%）持平。
  • 组件会过期。Anthropic Labs 2026 年 3 月的原话：harness 里每个组件都编码了一个"模型自己做不到"的假设。Sonnet 4.5 需要的上下文重置，到 Opus 4.5 就整个删掉了。Noam Brown 的立场是 scaffold 终将被推理模型取代。

把两边合起来看：harness 的价值主要在抬高下限、降低成本、长任务和真实仓库场景；它的具体内容有半衰期，但"模型和世界之间需要一层"这个角色不会消失。所以学 harness 工程，重点是学方法（发现失败、定位缺失的能力、机械化地堵上、评测、随模型升级做减法），而不是背某个固定架构。

练习：用自己的话向同事解释 harness，并举一个"同模型不同 harness 分数不同"的例子。

第 1 课一个 Agent 的最小骨架：循环

Thorsten Ball 2025 年 4 月《How to Build an Agent》的名句："It's an LLM, a loop, and enough tokens." 一个 agent 本质上是：把对话历史发给模型；模型要么回答，要么说"我要调用某个工具"；你执行工具，把结果追加到历史，再发一次；直到模型不再要工具。

协议要点（Claude Messages API，2026 年 10 月版本）

  • 工具定义：{name, description, input_schema}，input_schema 是 JSON Schema。
  • 模型返回的 stop_reason 为 tool_use 时，content 里有一个或多个 tool_use 块，每块有 id、name、input（已经是 dict，不用再解析）。
  • 把模型的整段 content 原样追加为 assistant 消息，然后追加一条 user 消息，内容是 tool_result 块列表：{type: "tool_result", tool_use_id, content, is_error?}。
  • 并行调用时所有 tool_result 必须放在同一条 user 消息里，且排在任何文本之前，否则 400。拆成多条消息会"悄悄训练模型不再并行调用"。
  • 工具失败不要吞掉，返回 is_error: true 和一段"错在哪、下一步试什么"的说明，模型会自行重试两三次。
  • 其他 stop_reason 要处理：end_turn（做完了）、max_tokens（输出被截断，最后一块可能是残缺的 tool_use，加大 max_tokens 重试）、refusal、model_context_window_exceeded。
  • 模型 id：claude-opus-5-5（官方推荐默认）、claude-sonnet-5-5、claude-haiku-5-5（便宜，练习用）、claude-fable-5-1。5.5 代模型不支持强制 tool_choice: any/tool，用 auto 加提示词措辞。

最小循环（mini_harness.py 的 run() 去掉日志和验证后的核心）

def run(task):
    client = anthropic.Anthropic()
    system = build_system()                       # 只构建一次
    messages = [{"role": "user", "content": task}]
    for step in range(1, MAX_STEPS + 1):          # 铁律 2: 有上限
        r = client.messages.create(model=MODEL, max_tokens=8000,
                                   system=system, tools=TOOLS, messages=messages)
        if r.stop_reason == "end_turn":
            return "".join(b.text for b in r.content if b.type == "text")
        if r.stop_reason != "tool_use":
            raise RuntimeError(r.stop_reason)
        results = []
        for block in r.content:
            if block.type != "tool_use":
                continue
            try:
                out = DISPATCH[block.name](**block.input)      # 工具内部已截断
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
            except Exception as e:                             # 错误回灌, 不吞
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": f"{type(e).__name__}: {e}", "is_error": True})
        messages.append({"role": "assistant", "content": r.content})   # 铁律 1: 原样追加
        messages.append({"role": "user", "content": results})          # 同一条消息
    raise RuntimeError("step limit reached")

三条铁律现在就养成习惯：

  1. 历史只追加，不回头修改。原因见第 5 课（缓存）和第 6 课。
  2. 必须有步数上限。官方文档的参考实现用 MAX_STEPS = 20。
  3. 工具结果在进入 messages 之前就截断，而不是事后删历史。

SDK 还提供了 tool runner（@beta_tool 装饰器加 client.beta.messages.tool_runner(...).until_done()，带 max_iterations），可以把循环折叠掉。先手写一遍再用它，否则遇到 400 你不知道是哪条规则被破坏了。

第 2 课给它手和眼睛：工具设计（ACI）

SWE-agent 论文把这件事叫 agent-computer interface：模型是你的"用户"，界面要为它设计。他们在 SWE-bench Lite 上用 GPT-4 Turbo 做的消融实验（基线 18.0%）值得背下来：

改动分数说明
编辑命令不带 linter 校验15.0语法错误没有即时反馈
完全没有编辑命令10.3影响最大
搜索返回原始长列表而非摘要12.0比完全没有搜索（15.7）还差
文件查看窗口 30 行 / 整个文件14.3 / 12.7100 行窗口最好
保留全部历史而非最近 5 条观察15.0上下文越多越差

由此得到四条设计原则：动作简单、选项少、文档短；把常用操作合并成少数紧凑动作；反馈信息量大但简洁；用 linter 一类护栏让 agent 能快速发现并纠正错误。

我们的四个工具及设计理由（完整实现见 mini_harness.py）

  • read_file(path, offset, limit)：返回带行号的文本，默认 200 行，并提示"共 N 行，用 offset=... 继续"。行号让 edit_file 能精确定位；分页是为了上下文。
  • list_files(pattern)：跳过隐藏目录、node_modules、__pycache__，最多 200 条。
  • edit_file(path, old_string, new_string)：old_string 必须恰好匹配一次，否则报错并提示"多复制几行上下文"；成功后返回 unified diff 供模型自检。Ball 原文里有个经典 bug：描述说只匹配一次，代码却 replace all。
  • run_command(command, timeout)：合并 stdout/stderr，返回 exit code；超时杀整个进程组；输出超过 1 万字符保留头尾各 5 千；环境里设 PAGER=cat 防止卡在分页器。

所有路径都经过 _resolve()，不允许逃出工作目录。

Anthropic 的工具原则（来自《Building effective agents》和《Writing effective tools for agents》）

  • Poka-yoke：把参数改成不容易用错的形式。他们的 SWE-bench agent 老用错相对路径，于是改成强制绝对路径。
  • 描述要像写给新同事：参数名用 user_id 而不是 user；工具之间功能不重叠。"如果人类工程师说不清该用哪个工具，模型也会困惑。"
  • 返回有意义的内容：返回 name 而不是 uuid；需要时提供 response_format: concise|detailed，他们测到简洁格式只有详细格式三分之一的 token。
  • 工具数量不是越多越好。OpenAI 的指南：15 个以上边界清晰的工具没问题，10 个以下但相互重叠就会出事。Claude Code 每个工具结果默认上限 2.5 万 token。
  • 他们花在优化工具上的时间比优化整体 prompt 还多。

bash-only 的反面教材。mini-SWE-agent 只给一个 bash 工具就能超过 74%；2026 年 9 月的研究（arXiv 2609.20804）也发现 bash 能力强的模型用 bash-only 接口效果好且更便宜，预定义工具主要帮助 bash 弱的模型。实践建议：先用 bash 覆盖面，当你需要对某类动作做拦截、渲染、审计或并行时，再把它提升为专用工具。send_email 可以被拦截，bash -c "curl -X POST ..." 不行。

练习：把 edit_file 的唯一匹配检查去掉，给模型一个有重复代码的文件，看它会改坏什么。

第 3 课告诉它规矩：系统提示与 CLAUDE.md / AGENTS.md

系统提示的"合适海拔"。Anthropic 的建议：介于"脆弱的 if-else 流程"和"空泛的指导"之间；最小但不等于短；在最好的模型上从最小集合开始，根据观察到的失败逐条增加。aider 2023 年测过"情绪化激励"（"用户是盲人"、"给 2000 美元小费"），结果反而降分。

项目说明文件。CLAUDE.md（Claude Code）和 AGENTS.md（Codex、Cursor、Aider 等 6 万多个项目通用的开放格式，由 Linux 基金会下的 Agentic AI Foundation 维护）是同一个思路：仓库里一份给 agent 看的 README，每次会话自动加载。

  • 放什么：模型猜不到的构建和测试命令、与默认不同的代码风格、仓库礼仪、架构决策、环境坑。
  • 不放什么：读代码就能知道的事、标准约定、详细 API 文档、经常变的信息、教程。
  • 判断标准："删掉这条，agent 会不会犯错？"
  • 长度：Claude Code 建议每个文件 200 行以内，"臃肿的 CLAUDE.md 会让 Claude 忽略你真正的指令"；Codex 把所有 AGENTS.md 拼起来后截断到 32 KiB；OpenAI 内部那个百万行仓库的 AGENTS.md 只有约 100 行。
  • 分层：全局（~/.claude 或 ~/.codex）→ 仓库根 → 子目录，越靠近工作目录的越后加载、优先级越高。

OpenAI 的"地图不是手册"。他们试过一个巨大的 AGENTS.md，失败原因四条：上下文稀缺，巨型文件挤掉任务和代码；什么都重要等于什么都不重要；立刻过时，变成"陈旧规则的坟场"；无法机械校验。解法是 AGENTS.md 只做目录，指向 docs/ 里结构化的设计文档、架构地图、质量评级、执行计划，再用 linter 和 CI 保证文档互链和新鲜，另外跑一个定期的"文档园丁"agent 清理过时内容。

关键区分：建议 vs 强制。CLAUDE.md、skills、系统提示都是建议，模型可以不听。Claude Code 文档原话："CLAUDE.md 里写'不要编辑 .env'是请求，不是保证；一个阻止编辑的 PreToolUse hook 才是强制。"第 4 课讲强制。

我们的加载方式：

def build_system():
    text = ("You are a careful coding agent working inside the workspace ...\n"
            "Rules:\n- Read a file before you edit it. ...\n"
            "- Never edit or delete tests to make them pass.\n"
            "- Run the test suite before claiming the task is done ...")
    for name in ("AGENTS.md", "CLAUDE.md"):
        f = WORKDIR / name
        if f.exists():
            text += f'\n\n<project_instructions source="{name}">\n{f.read_text()[:20_000]}\n</project_instructions>'
            break
    return [{"type": "text", "text": text, "cache_control": {"type": "ephemeral"}}]

system 只在任务开始时构建一次，循环中不再变动，否则前缀缓存全部失效。

练习：给示例仓库的 AGENTS.md 加一条模型猜不到的规则（比如"提交前运行 ruff"），跑同一任务，看轨迹里它有没有照做；再删掉这条，比较差异。

第 4 课别让它闯祸：权限、确认与沙箱

三个层次，由浅入深：

  1. 进程级：工作目录限制、只读命令白名单、其余命令先问人、超时。mini_harness.py 实现了这一层。
  2. 容器级：把 subprocess 换成 docker exec，每个任务一个干净镜像。mini-SWE-agent 就是这么切换的。
  3. 操作系统级：macOS Seatbelt、Linux bubblewrap 加 seccomp。Claude Code 和 Codex CLI 都用这套：只允许写当前目录，网络默认关闭或经代理按域名放行，.git、.claude、.codex、.aws 等路径永不自动放行。Anthropic 开源了 sandbox-runtime，他们内部数据是沙箱让权限弹窗减少 84%。

为什么弹窗不是答案。Anthropic 的数据：用户对手动权限提示 93% 都点了同意。于是他们做了 auto mode，用一个独立分类器模型审每个会改状态的动作，连续拦 3 次或累计 20 次就退回人工确认。分类器看不到工具结果，所以网页或文件里的恶意文本无法直接操纵它。

Hooks 是强制机制。Claude Code 和 Codex CLI 都有生命周期钩子：PreToolUse、PostToolUse、Stop、PreCompact、SessionStart 等。约定一致：退出码 0 放行，退出码 2 阻止并把 stderr 作为理由回灌给模型。Claude Code 文档的建议："任何必须每次都发生、零例外的事，写成 hook。"hook 不占上下文。

我们的实现：

SAFE_PREFIXES = ("ls", "cat ", "head ", "tail ", "wc ", "find ", "grep ", "rg ",
                 "git status", "git diff", "git log", "pytest", "python -m pytest")

def gate(command):
    if os.environ.get("HARNESS_YOLO"):          # 只在一次性容器里打开
        return
    if command.strip().startswith(SAFE_PREFIXES):
        return
    if input(f"[permission] run `{command}` ? [y/N] ").strip().lower() != "y":
        raise PermissionError("The user declined to run this command. "
                              "Try a different approach or explain what you need and why.")

白名单只放只读命令；拒绝时返回给模型的不是异常栈，而是一句可执行的指令。注意白名单是基于前缀的粗筛，cat x; rm -rf y 这类拼接命令会漏过去，这正是为什么生产工具最终都走到了操作系统级沙箱。

练习：让 agent 执行删除目录的命令，确认被拦；再把该命令加进白名单，体会"白名单就是信任边界"。

第 5 课上下文是最稀缺的资源

证据

  • Chroma 2025 年 7 月测了 18 个模型：输入越长，即使是简单任务表现也下降；一个干扰项就有害，四个叠加更糟；LongMemEval 上 300 token 的聚焦输入显著好于 11.3 万 token 的全量输入。
  • "Lost in the Middle"（2023）：相关信息在开头或结尾时效果最好，在中间显著下降。
  • Anthropic 把这叫 context rot，根因是 n² 注意力加上长序列训练数据稀缺，所以上下文是"边际收益递减的有限资源"。Claude Code 文档说"大多数最佳实践都基于一个约束：上下文窗口填得很快，而且越满性能越差"。

四种技术（按复杂度排序）

  1. 在工具层截断。进入 messages 之前就裁：输出头尾各 5 千字符；读文件分页；搜索限 100 条。2026 年 9 月的研究发现"规则截断先于 LLM 摘要"最省钱，而让被删内容可恢复的机制"模型很少用"。
  2. 压缩（compaction）。Claude Code 先清旧工具输出，再对话摘要，保留请求和关键代码片段，摘要后带上最近访问的 5 个文件；如果单个输出大到摘要后立刻又满，就停止自动压缩并报错而不是死循环。OpenHands 的 condenser 保留前 N 条和后 M 条事件，中间交给 LLM 摘要。Codex 用服务端 /responses/compact。
  3. 结构化笔记。把状态写到文件而不是留在窗口里：进度文件、todo、JSON 特性清单。Manus 的"复述"技巧是不断重写 todo.md，让目标始终出现在注意力最近的位置；一个任务平均 50 次工具调用，不复述就会跑偏。
  4. 子代理。子代理用自己的窗口干脏活，只返回 1000 到 2000 token 的摘要。Claude Code 的 Explore 子代理就是为此存在。

Manus 的六条生产经验（2025-07，很多 harness 隐性规则的来源）

  • KV 缓存命中率是生产 agent 最重要的指标：缓存输入 0.30 美元/百万 token，未缓存 3 美元，差 10 倍；输入输出比约 100:1。
  • 前缀必须稳定：系统提示里放一个精确到秒的时间戳就会把缓存全毁掉；序列化要确定性。
  • 上下文只追加。
  • 工具"屏蔽而不删除"：任务中途增删工具会打破缓存，还会让历史里引用了已删除工具的地方让模型困惑。
  • 文件系统就是无限且持久的记忆；压缩要可恢复（删网页内容但留 URL）。
  • 把错误留在上下文里。失败的动作和堆栈让模型更新信念；"错误恢复是真正 agent 行为最清晰的指标"。

对应到代码：第 1 课的只追加、truncate()、每步把 usage 整个记进轨迹。Claude 的缓存规则：按 tools → system → messages 顺序做前缀匹配，必须完全一致；最短可缓存 512 token（5.5 代模型）；5 分钟 TTL，可选 1 小时；读价为基础价的 10%（Opus/Sonnet 5.5 为 5%，Fable 5.1 为 2.5%）。usage 里 cache_read_input_tokens 和 cache_creation_input_tokens 都是 0 就说明没命中。另外 2026 年 8 月 31 日之后创建的账号，API 会校验历史是否被改动过，改了直接 400，只追加不再只是优化而是硬要求。

练习：跑一个需要读大文件的任务，分别用 limit=2000 和 limit=200，比较轨迹里的总 token 和成本。

第 6 课什么时候算做完：停止条件与验证

两类失败。一类是停不下来：死循环、反复读同一个文件、格式错误。另一类更隐蔽：过早宣布胜利。Anthropic 观察到 agent "看到一些进展就宣布项目完成"，或者只跑了单元测试、curl 一下就把特性标成通过；Terminal-Bench 的失败分类里有 "Premature Termination" 和 "Weak Verification"；Claude Code 文档的解释是"没有一个它能运行的检查时，'看起来做完了'是唯一的信号"。

硬上限（mini-SWE-agent 的默认值是很好的参考）：步数、费用（默认 3 美元）、墙钟时间、连续格式错误（3 次）。官方参考实现另加 MAX_CONTINUATIONS = 5。

把成功信号放到 agent 够不到的地方。所有有效做法都是同一个原理：

  • 测试不能改。Anthropic 长任务 harness 的 prompt 原话："删除或修改测试是不可接受的。"2026 年的研究显示 80.2% 的 agent 自写测试缺乏有效断言；有 agent 把公开测试的期望输出预计算进查找表，公开集 97%、留出集 0%。
  • 端到端验证。用浏览器自动化点一遍，而不是只看单测；OpenAI 让 Codex 修 bug 前后各录一段视频附在 PR 上。
  • 做的人和判的人分开。Anthropic 的 generator/evaluator：独立的怀疑型评估者比让生成者自我批评"可处理得多"；Claude Code 文档建议用新上下文的子代理做对抗式审查，因为"模型不会偏袒自己刚写的代码"，同时提醒"被要求找问题的审查者通常都会报告一些问题"。
  • 状态用 JSON 而不是 Markdown 存：模型更少乱改 JSON；特性清单里 agent 只能翻 passes 字段。

我们的实现：--require-tests 开关。模型说做完时，如果轨迹里没有跑过 pytest，harness 回一句"你还没跑测试"，最多两次。这就是 Claude Code Stop hook 的玩具版：

if r.stop_reason == "end_turn":
    if require_tests and not ran_tests and nudges < 2:
        nudges += 1
        messages.append({"role": "assistant", "content": r.content})
        messages.append({"role": "user", "content": "[harness] You have not run the test suite yet. "
                         "Run it with pytest, fix any failure, then give your final summary."})
        continue
    return ...

示例任务的 check.py 则演示了"把信号放在 agent 够不到的地方"：它在仓库外部运行，先比对测试文件有没有被改，再用自己的断言（含一个隐藏用例）检查行为。

练习：把 tasks/fix_add/repo/calc.py 里的 bug 改成更隐蔽的（比如只在负数时出错），关掉 --require-tests，看模型会不会宣布完成。

第 7 课你怎么知道改好了：评测

Anthropic《Demystifying evals for AI agents》（2026-01）的术语：task（输入加成功标准）、trial（一次尝试）、grader（打分逻辑）、transcript（完整轨迹）、outcome（最终环境状态，是"数据库里真的有这条预订"而不是"agent 说它订了"）。评测 agent 就是评测 harness 和模型的组合。

起步规则

  • 从真实失败里抽 20 到 50 个简单任务。好任务的标准：两位专家会给出同样的判决。
  • 每次 trial 从干净环境开始（他们遇到过 agent 从上次 trial 的 git 历史里偷看答案）。
  • 优先确定性 grader（测试、字符串匹配、状态检查），评结果不评路径；LLM 评委要给 "Unknown" 选项、用和被测 agent 不同的模型家族。
  • 多跑几次。pass@k 是 k 次里至少一次成功，pass^k 是 k 次全成功。单次 75% 的任务，pass^3 只有 42%。
  • 读轨迹。失败要"看起来公平"。他们有个案例：Opus 4.5 在 CORE-Bench 从 42% 到 95%，只是修了评分和任务描述的问题并换了限制更少的 scaffold。
  • 费用和 token 是和通过率并列的坐标轴。

我们的实现：mini_eval.py 加 tasks/<name>/{repo/, prompt.txt, check.py}。每个任务拷贝到临时目录跑 n 次，check.py 从仓库外部检查结果，每次 trial 写一行 JSONL（通过与否、步数、成本、轨迹路径），最后打印每个任务的 pass@1、pass^k、平均成本。成本按 usage 的四个字段乘价格表估算。

HARNESS_MODEL=claude-haiku-5-5 python mini_eval.py --trials 3

练习：再写 4 个任务（改 bug、加功能、重构、写文档各一个），跑 3 次，找出 pass^3 最低的那个，读它的轨迹，然后只改 harness（不改模型、不改任务）把它修好。这一步就是 Hashimoto 定义的 harness 工程本身。

第 8 课长任务与多代理：进阶模式

Anthropic 的长任务配方（2025-11，几乎只用文件加 git，不需要额外代码）

  • 初始化会话写三样东西：init.sh（怎么启动应用）、claude-progress.txt（进度日志）、一个 JSON 特性清单（200 多条，全部 passes: false），然后做第一次 git 提交。
  • 之后每个编码会话的固定开场：pwd，读 git log 和进度文件，读清单挑最高优先级未完成的一条，跑 init.sh，先做一次基本的端到端检查，再开始干活。
  • 一次只做一个特性，做完用浏览器自动化验证，提交，更新进度文件。留下的代码要"可以合并到主干"。
  • 对应修掉的失败：过早宣布胜利、半成品没记录、没测试就标完成、每次重新摸索怎么启动。

同一思路的大规模版本：2026 年 2 月 Anthropic 用 16 个并行 Claude Code 在 Docker 里写了一个约 10 万行 Rust 的 C 编译器。while true 循环不断开新会话，任务认领靠 git 里的锁文件，没有中央调度器，约 2000 个会话、不到 2 万美元。期间有一个 agent 跑了 pkill -9 bash。

Ralph Wiggum 循环（Geoffrey Huntley，2025-07）：while :; do cat PROMPT.md | claude-code; done。同一个 prompt，每轮全新上下文，一轮只做一件事，靠测试、类型检查、静态分析提供"背压"。只适合从零开始的项目。

生成者/评估者（Anthropic Labs，2026-03）：planner 把一两句话扩成产品规格，generator 按特性冲刺，evaluator 用 Playwright 像用户一样点。代价明确：同一个任务单 agent 20 分钟 9 美元，完整 harness 6 小时 200 美元，超过 20 倍。"当任务超出当前模型独立可靠完成的范围时才值得。"到 Opus 4.6 他们就删掉了冲刺机制，评估者只留最后一轮。

多代理的坑。Cognition《Don't Build Multi-Agents》（2025-06）：两条原则，共享完整轨迹而不只是消息；动作携带隐含决策，冲突的决策产生坏结果。例子是让两个子代理分别做 Flappy Bird 的背景和小鸟，拼不到一起。推荐单线程线性 agent，长任务用专门的压缩模型。Anthropic 的多代理研究系统则显示并行子代理在研究类任务上比单 Opus 4 强 90.2%，但 token 用量是聊天的 15 倍，"并行和专业化必须赚回协调成本"。经验法则：并行用于读和搜（结果可合并），不用于写同一份代码。

OpenAI 的仓库级 harness（2026-02 那篇博客的技术清单，适合已经在用 agent 写生产代码的团队）

  • 上下文：约 100 行的 AGENTS.md 当目录；docs/ 做知识库（设计文档含验证状态、架构地图、质量评级、执行计划含决策日志、技术债）；渐进披露。
  • 机械反馈：固定分层 Types → Config → Repo → Service → Runtime → UI，只能向前依赖，横切关注点只能经 Providers 进入；用 Codex 自己写的自定义 linter 和结构化测试强制；linter 的报错文案直接写成给 agent 的修复指令。"强制不变量，不微管实现。"
  • 感知：应用按 git worktree 可独立启动；Chrome DevTools Protocol 做 DOM 快照和截图；每个 worktree 一套临时可观测性栈，agent 用 LogQL 和 PromQL 查日志和指标。
  • 维护自动化：文档园丁 agent；"黄金原则"加定期 GC 任务扫描偏差、开小型重构 PR 并自动合并（之前他们每周五花 20% 时间清 "AI slop"）；agent 对 agent 的代码审查循环。
  • 合并哲学：最小阻塞门禁，"吞吐远超人类注意力时，纠错便宜，等待昂贵"。
  • 核心信念："从 agent 的角度看，运行时拿不到的东西就不存在。"Google Docs、聊天记录、人脑里的知识对系统不可见。

第 9 课把这些对照到你每天用的工具

Claude Code 的功能可以放进一个 2×2：

建议性（模型可不听）强制性
常驻上下文CLAUDE.md、.claude/rules/、auto memory权限模式、沙箱、保护路径
按需加载或零上下文skills（只常驻描述，1536 字符）、MCP（只常驻工具名，用到才加载 schema）、子代理（隔离窗口）hooks（零上下文，exit 2 阻断）、worktree 隔离检查

值得记住的数字：工具输出上限 2.5 万 token；MCP 输出 1 万警告、2.5 万截断；CLAUDE.md 200 行；SKILL.md 500 行；默认 20 个并发子代理、3 层嵌套；auto mode 连续 3 次或累计 20 次拦截就退回人工。

Codex CLI 的对应项：AGENTS.md 分层拼接、32 KiB 上限；approval_policy（on-request / never / 细粒度表）加 sandbox_mode（read-only / workspace-write / danger-full-access）；hooks 12 个事件、默认开启、exit 2 阻断；skills 列表占上下文 2%；子代理默认开；服务端 compaction。OpenAI 内部人士承认"Codex 模型是在 harness 存在的情况下训练的"，这解释了为什么同一模型在自家 harness 里分数更高，也解释了为什么换工具有时会退步。

官方给的"什么时候用哪个"触发表（Claude Code 文档）：

  • 同一个约定或命令错了两次 → 写进 CLAUDE.md
  • 第三次粘贴同一套操作手册 → 做成 skill
  • 某个旁支任务的输出淹没了对话 → 交给子代理
  • 某件事必须每次都发生、不要问 → 写 hook
  • 第二个仓库需要同样的配置 → 打包成 plugin
  • 两次纠正都没用 → /clear，重写初始 prompt

练习：打开你常用工具的配置目录，把现有的 CLAUDE.md / AGENTS.md / hooks / skills 填进上面的 2×2 表，看哪个格子是空的，想想为什么。

第 10 课心法与反模式

心法

  • 失败是信号，不是让它"再努力点"。OpenAI："修复几乎从来不是 try harder"，而是问"缺了什么能力，怎么让它对 agent 既可见又可强制"。Hashimoto：每个错误只允许犯一次。
  • 好 harness 与坏 harness（Daniel Miessler）：坏的是逐步说明书式的 prompt，试图比模型聪明；好的是环境和验证。
  • 每个组件都是对"模型做不到"的假设，会过期。Amp 团队的检验问题：这段 harness 代码是在帮助 inspect、verify、recover、merge 模型的工作，还是在"照看昨天的模型"？新模型来了，先删不再承重的部分。
  • 从最简单的方案开始，只在需要时增加复杂度。OpenAI 指南：先把单 agent 的能力榨干，分支逻辑复杂或工具重叠时才拆。
  • 协同训练的现实：harness 里的补丁会迁移进下一代模型，但"模型和外部上下文、工具之间的接口"会留下。所以具体技巧要常更新，方法论不会过时。

反模式清单（都有出处）

  • 大杂烩提示和臃肿的 CLAUDE.md："强调的东西太多，就没有一条突出。"
  • 工具过载：Vercel 把工具从 15 个砍到 2 个，成功率 80% → 100%。
  • 多代理分散决策（Cognition 的 Flappy Bird）。
  • 过早宣布胜利；改测试让它通过；自己给自己打分（分数会漂高）。
  • 事后修改历史：破坏缓存，新账号直接 400。
  • 系统提示里放时间戳、随机 id 等易变内容。
  • 相信 prompt 里的"禁止"：仅靠 prompt 的工具访问控制会漏掉 4% 到 37% 的未授权调用；要拦就用 hook 或沙箱。
  • 情绪化激励、威胁、小费：aider 实测降分。
  • 一次 trial 定胜负：用 pass^k 看稳定性。
  • 过时的配置文件：CLAUDE.md / AGENTS.md 没人维护，变成"陈旧规则的坟场"。给它指定 owner，像审代码一样审它的改动。
