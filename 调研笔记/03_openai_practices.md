### Q1. The OpenAI "Harness engineering" blog post: identity, numbers, and every concrete technique

**Takeaway**
The post is "Harness engineering: leveraging Codex in an agent-first world" (openai.com/index/harness-engineering, published 2026-02-11 per secondary coverage; author Ryan Lopopolo per the Latent Space interview and press, byline not visible in the fetched text). A team of 3 (later 7) engineers wrote 0 lines of code by hand over ~5 months (first commit late Aug 2025), producing ~1M LOC and ~1,500 merged PRs (3.5 PRs/engineer/day). Its thesis: "Humans steer. Agents execute." The engineer's job becomes designing environments, specifying intent, and building feedback loops; every technique in the post is a way to make the repo "legible" to the agent and to enforce invariants mechanically.

**Cited Findings — identity and headline numbers**
- Exact title: "Harness engineering: leveraging Codex in an agent-first world" — [OpenAI](https://openai.com/index/harness-engineering/) (title confirmed from fetched page text).
- Date 2026-02-11 and author Ryan Lopopolo are reported by secondary coverage (byline/date were not present in the proxied page text I could fetch) — [letsdatascience summary](https://letsdatascience.com/news/openai-introduces-harness-engineering-for-automated-developm-703d90b6); [InfoQ Japan, March 2026](https://www.infoq.com/jp/news/2026/03/openai-harness-engineering-codex/). The Latent Space podcast (Apr 7, 2026) introduces Lopopolo ("Frontier Product Exploration at OpenAI") as the author of "a lengthy essay titled 'Harness Engineering'" — [Latent Space](https://latent.space/p/harness-eng).
- Opening claim: "building and shipping an internal beta of a software product with **0 lines of manually-written code**" ... "every line of code—application logic, tests, CI configuration, documentation, observability, and internal tooling—has been written by Codex. We estimate that we built this in about 1/10th the time it would have taken to write the code by hand." — [OpenAI](https://openai.com/index/harness-engineering/)
- "**Humans steer. Agents execute.**" — [OpenAI](https://openai.com/index/harness-engineering/)
- Redefinition of the job: "what changes when a software engineering team's primary job is no longer to write code, but to design environments, specify intent, and build feedback loops that allow Codex agents to do reliable work." — [OpenAI](https://openai.com/index/harness-engineering/)
- Scarce resource framing: "how to maximize our one truly scarce resource: human time and attention." — [OpenAI](https://openai.com/index/harness-engineering/)
- Timeline/size: "The first commit to an empty repository landed in late August 2025." ... "Five months later, the repository contains on the order of a million lines of code ... roughly 1,500 pull requests have been opened and merged with a small team of just three engineers driving Codex. This translates to an average throughput of 3.5 PRs per engineer per day, and surprisingly the throughput has _increased_ as the team has grown to now seven engineers." — [OpenAI](https://openai.com/index/harness-engineering/)
- Bootstrapping: "The initial scaffold—repository structure, CI configuration, formatting rules, package manager setup, and application framework—was generated by Codex CLI using GPT‑5, guided by a small set of existing templates. Even the initial AGENTS.md file ... was itself written by Codex." — [OpenAI](https://openai.com/index/harness-engineering/)
- Human/agent split: "Throughout the development process, humans never directly contributed any code. This became a core philosophy for the team: **no manually-written code**." Humans "prioritize work, translate user feedback into acceptance criteria, and validate outcomes." "Humans may review pull requests, but aren't required to. Over time, we've pushed almost all review effort towards being handled agent-to-agent." — [OpenAI](https://openai.com/index/harness-engineering/)
- Long runs: "We regularly see single Codex runs work on a single task for upwards of six hours (often while the humans are sleeping)." — [OpenAI](https://openai.com/index/harness-engineering/)
- Podcast-only numbers (not in the post): PRs per engineer rose from ~3.5/day in December to 5–10/day after GPT-5.2; the team spends on the order of 1B tokens/day (host estimate $2–3k/day) and Lopopolo calls running below that "borderline negligent"; most review happens after merge and is often skipped; humans still approve a smoke test before release — [Latent Space, "Extreme Harness Engineering for Token Billionaires: 1M LOC, 1B toks/day, 0% human code, 0% human review", Apr 7 2026](https://latent.space/p/harness-eng). Treat the token/$ figures as podcast conversation, not an official metric.

**Cited Findings — the techniques, section by section (post headings in order)**
1. "Redefining the role of the engineer"
- Root-cause framing of failures: "Early progress was slower than we expected, not because Codex was incapable, but because the environment was underspecified. The agent lacked the tools, abstractions, and internal structure required to make progress." "When something failed, the fix was almost never 'try harder.' ... human engineers always stepped into the task and asked: 'what capability is missing, and how do we make it both legible and enforceable for the agent?'" — [OpenAI](https://openai.com/index/harness-engineering/)
- Depth-first decomposition: "breaking down larger goals into smaller building blocks (design, code, review, test, etc), prompting the agent to construct those blocks, and using them to unlock more complex tasks." — [OpenAI](https://openai.com/index/harness-engineering/)
- Self-review loop: "we instruct Codex to review its own changes locally, request additional specific agent reviews both locally and in the cloud, respond to any human or agent given feedback, and iterate in a loop until all agent reviewers are satisfied (effectively this is a Ralph Wiggum Loop)." Codex "uses our standard development tools directly (gh, local scripts, and repository-embedded skills)". — [OpenAI](https://openai.com/index/harness-engineering/) (links ghuntley.com/loop/ for the Ralph Wiggum Loop)
- Podcast detail on review agents: reviewers are told to favour merging and flag only P2-or-higher issues; author agents are explicitly allowed to push back on or defer reviewer feedback, because otherwise the author agent "kept yielding to reviewers" — [Latent Space](https://latent.space/p/harness-eng)

2. "Increasing application legibility" (letting the agent see the running app)
- "our bottleneck became human QA capacity ... we've worked to add more capabilities to the agent by making things like the application UI, logs, and app metrics themselves directly legible to Codex." — [OpenAI](https://openai.com/index/harness-engineering/)
- Browser: "we made the app bootable per git worktree, so Codex could launch and drive one instance per change. We also wired the Chrome DevTools Protocol into the agent runtime and created skills for working with DOM snapshots, screenshots, and navigation. This enabled Codex to reproduce bugs, validate fixes, and reason about UI behavior directly." — [OpenAI](https://openai.com/index/harness-engineering/)
- Observability: "Logs, metrics, and traces are exposed to Codex via a local observability stack that's ephemeral for any given worktree ... torn down once that task is complete. Agents can query logs with LogQL and metrics with PromQL. With this context available, prompts like 'ensure service startup completes in under 800ms' or 'no span in these four critical user journeys exceeds two seconds' become tractable." — [OpenAI](https://openai.com/index/harness-engineering/)
- Podcast detail: instead of Playwright-through-MCP they built a small CLI shim; for layout checks they rasterize the UI to an image for the model; agents attach videos to PRs as trust signals; dashboards are defined as code and Codex answers pages using them — [Latent Space](https://latent.space/p/harness-eng)

3. "We made repository knowledge the system of record" (AGENTS.md as map; docs/ as knowledge base)
- Core lesson: "give Codex a map, not a 1,000-page instruction manual." — [OpenAI](https://openai.com/index/harness-engineering/)
- Why one big AGENTS.md failed (four bullets, quoted): "**Context is a scarce resource.** A giant instruction file crowds out the task, the code, and the relevant docs"; "**Too much guidance becomes non-guidance.** When everything is 'important,' nothing is."; "**It rots instantly.** A monolithic manual turns into a graveyard of stale rules ... the file quietly becomes an attractive nuisance."; "**It's hard to verify.** A single blob doesn't lend itself to mechanical checks (coverage, freshness, ownership, cross-links), so drift is inevitable." — [OpenAI](https://openai.com/index/harness-engineering/)
- "So instead of treating `AGENTS.md` as the encyclopedia, we treat it as **the table of contents**." "A short `AGENTS.md` (roughly 100 lines) is injected into context and serves primarily as a map, with pointers to deeper sources of truth elsewhere." — [OpenAI](https://openai.com/index/harness-engineering/)
- docs/ contents: "The repository's knowledge base lives in a structured `docs/` directory treated as the system of record." It holds: design documentation "catalogued and indexed, including verification status and a set of core beliefs that define agent-first operating principles"; architecture documentation (links matklad's ARCHITECTURE.md essay) giving "a top-level map of domains and package layering"; "A quality document grades each product domain and architectural layer, tracking gaps over time"; plans as "first-class artifacts": "Ephemeral lightweight plans ... for small changes, while complex work is captured in execution plans with progress and decision logs that are checked into the repository. Active plans, completed plans, and known technical debt are all versioned and co-located." — [OpenAI](https://openai.com/index/harness-engineering/) (the execution-plans link goes to cookbook.openai.com/articles/codex_exec_plans)
- "This enables **progressive disclosure**: agents start with a small, stable entry point and are taught where to look next, rather than being overwhelmed up front." — [OpenAI](https://openai.com/index/harness-engineering/)
- Doc gardening: "We enforce this mechanically. Dedicated linters and CI jobs validate that the knowledge base is up to date, cross-linked, and structured correctly. A recurring 'doc-gardening' agent scans for stale or obsolete documentation that does not reflect the real code behavior and opens fix-up pull requests." — [OpenAI](https://openai.com/index/harness-engineering/)
- Podcast detail: the repo has about six skills total; process gaps get encoded into existing skills; when a pager alert fires Codex is asked to fix it *and* update the reliability docs (example rule: timeouts on all network calls); session logs, PR comments and failed builds are periodically reviewed to update shared skills/docs — [Latent Space](https://latent.space/p/harness-eng)

4. "Agent legibility is the goal" (what "legibility" means; boring tech; context in repo)
- "From the agent's point of view, anything it can't access in-context while running effectively doesn't exist. Knowledge that lives in Google Docs, chat threads, or people's heads are not accessible to the system. Repository-local, versioned artifacts (e.g., code, markdown, schemas, executable plans) are all it can see." — [OpenAI](https://openai.com/index/harness-engineering/)
- "That Slack discussion that aligned the team on an architectural pattern? If it isn't discoverable to the agent, it's illegible in the same way it would be unknown to a new hire joining three months later." — [OpenAI](https://openai.com/index/harness-engineering/)
- "Giving Codex more context means organizing and exposing the right information so the agent can reason over it, rather than overwhelming it with ad-hoc instructions." — [OpenAI](https://openai.com/index/harness-engineering/)
- Dependency choice: "Technologies often described as 'boring' tend to be easier for agents to model due to composability, api stability, and representation in the training set. In some cases, it was cheaper to have the agent reimplement subsets of functionality than to work around opaque upstream behavior ... rather than pulling in a generic `p-limit`-style package, we implemented our own map-with-concurrency helper: it's tightly integrated with our OpenTelemetry instrumentation, has 100% test coverage". — [OpenAI](https://openai.com/index/harness-engineering/)

5. "Enforcing architecture and taste" (mechanical constraints; instructive linters)
- "**By enforcing invariants, not micromanaging implementations, we let agents ship fast without undermining the foundation.** For example, we require Codex to parse data shapes at the boundary, but are not prescriptive on how that happens (the model seems to like Zod, but we didn't specify that specific library)." — [OpenAI](https://openai.com/index/harness-engineering/)
- "Agents are most effective in environments with strict boundaries and predictable structure, so we built the application around a rigid architectural model. Each business domain is divided into a fixed set of layers, with strictly validated dependency directions and a limited set of permissible edges. These constraints are enforced mechanically via custom linters (Codex-generated, of course!) and structural tests." — [OpenAI](https://openai.com/index/harness-engineering/)
- The layering rule: "code can only depend 'forward' through a fixed set of layers (Types → Config → Repo → Service → Runtime → UI). Cross-cutting concerns (auth, connectors, telemetry, feature flags) enter through a single explicit interface: Providers. Anything else is disallowed and enforced mechanically." "This is the kind of architecture you usually postpone until you have hundreds of engineers. With coding agents, it's an early prerequisite". — [OpenAI](https://openai.com/index/harness-engineering/)
- Linters that teach: "we statically enforce structured logging, naming conventions for schemas and types, file size limits, and platform-specific reliability requirements with custom lints. Because the lints are custom, we write the error messages to inject remediation instructions into agent context." — [OpenAI](https://openai.com/index/harness-engineering/)
- "In a human-first workflow, these rules might feel pedantic or constraining. With agents, they become multipliers: once encoded, they apply everywhere at once." — [OpenAI](https://openai.com/index/harness-engineering/)
- Platform-org analogy: "enforce boundaries centrally, allow autonomy locally." Style tolerance: "The resulting code does not always match human stylistic preferences, and that's okay. As long as the output is correct, maintainable, and legible to future agent runs, it meets the bar." — [OpenAI](https://openai.com/index/harness-engineering/)
- Taste feedback loop: "Review comments, refactoring pull requests, and user-facing bugs are captured as documentation updates or encoded directly into tooling. When documentation falls short, we promote the rule into code". — [OpenAI](https://openai.com/index/harness-engineering/)
- NOTE: the phrase "make the agent's mistakes impossible" does not appear in the post; the closest wording is "so the agent can't accidentally build on guessed shapes" (see section 8 below) and "enforced mechanically". Mark the slogan as paraphrase, not quote. — [OpenAI](https://openai.com/index/harness-engineering/)

6. "Throughput changes the merge philosophy"
- "The repository operates with minimal blocking merge gates. Pull requests are short-lived. Test flakes are often addressed with follow-up runs rather than blocking progress indefinitely. In a system where agent throughput far exceeds human attention, corrections are cheap, and waiting is expensive. This would be irresponsible in a low-throughput environment. Here, it's often the right tradeoff." — [OpenAI](https://openai.com/index/harness-engineering/)
- Podcast detail: inner-loop build had to finish in under one minute; the team moved from Make through Bazel, Turborepo and Nx as models changed; background shells let the agent keep working during long builds — [Latent Space](https://latent.space/p/harness-eng)

7. "What 'agent-generated' actually means" and "Increasing levels of autonomy"
- Agents produce: "Product code and tests; CI configuration and release tooling; Internal developer tools; Documentation and design history; Evaluation harnesses; Review comments and responses; Scripts that manage the repository itself; Production dashboard definition files". "They pull review feedback, respond inline, push updates, and often squash and merge their own pull requests." — [OpenAI](https://openai.com/index/harness-engineering/)
- "When the agent struggles, we treat it as a signal: identify what is missing—tools, guardrails, documentation—and feed it back into the repository, always by having Codex itself write the fix." — [OpenAI](https://openai.com/index/harness-engineering/)
- End-to-end list from a single prompt: validate codebase state, reproduce bug, record a video of the failure, implement fix, validate by driving the app, record a second video, open PR, respond to feedback, detect and remediate build failures, "Escalate to a human only when judgment is required", merge. Caveat: "This behavior depends heavily on the specific structure and tooling of this repository and should not be assumed to generalize without similar investment—at least, not yet." — [OpenAI](https://openai.com/index/harness-engineering/)

8. "Entropy and garbage collection"
- Problem: "Codex replicates patterns that already exist in the repository—even uneven or suboptimal ones. Over time, this inevitably leads to drift." "Our team used to spend every Friday (20% of the week) cleaning up 'AI slop.' Unsurprisingly, that didn't scale." — [OpenAI](https://openai.com/index/harness-engineering/)
- Fix: "we started encoding what we call 'golden principles' directly into the repository and built a recurring cleanup process ... For example: (1) we prefer shared utility packages over hand-rolled helpers to keep invariants centralized, and (2) we don't probe data 'YOLO-style'—we validate boundaries or rely on typed SDKs so the agent can't accidentally build on guessed shapes. On a regular cadence, we have a set of background Codex tasks that scan for deviations, update quality grades, and open targeted refactoring pull requests. Most of these can be reviewed in under a minute and automerged." — [OpenAI](https://openai.com/index/harness-engineering/)
- "This functions like garbage collection. Technical debt is like a high-interest loan: it's almost always better to pay it down continuously in small increments than to let it compound and tackle it in painful bursts. Human taste is captured once, then enforced continuously on every line of code." — [OpenAI](https://openai.com/index/harness-engineering/)

9. "What we're still learning" (closing)
- "building software still demands discipline, but the discipline shows up more in the scaffolding rather than the code." "**Our most difficult challenges now center on designing environments, feedback loops, and control systems** that help agents accomplish our goal: build and maintain complex, reliable software at scale." Open questions: "how architectural coherence evolves over years", "where human judgment adds the most leverage and how to encode that judgment so it compounds". — [OpenAI](https://openai.com/index/harness-engineering/)

**Cited Findings — podcast-only concepts (Symphony, ghost libraries)**
- Symphony: an Elixir orchestration layer that spins up, supervises and re-runs many Codex agents across tickets; when a PR fails review the system discards it and restarts from scratch, then the team asks why the agent got it wrong — [Latent Space](https://latent.space/p/harness-eng)
- "Ghost libraries": distributing software as a detailed spec that a coding agent rebuilds, with other agents reviewing the result and refining the spec — [Latent Space](https://latent.space/p/harness-eng)
- Lopopolo's one-line rule: "the only fundamentally scarce thing is the synchronous human attention of my team." Also: "To let the model cook, you have to step back ... you need to take a systems thinking mindset" (transcript wording per podcast page) — [Latent Space](https://latent.space/p/harness-eng)
- Context minimalism rationale (podcast): the team prefers scripts/CLIs the agent calls over large tool-injection layers because MCP tool definitions are forced into context and can disrupt compaction — [Latent Space](https://latent.space/p/harness-eng)

**Inferences**
- The post's technique set decomposes cleanly into four tutorial-sized buckets: (a) context design (short AGENTS.md map + docs/ knowledge base + progressive disclosure), (b) mechanical feedback loops (custom linters with remediation text, structural tests, doc linters, CI), (c) perception tools (per-worktree app boot, CDP browser skills, LogQL/PromQL observability), (d) maintenance automation (doc-gardening agent, golden-principles GC tasks, agent-to-agent review loops).
- The recurring meta-rule, quoted three different ways, is: when the agent fails, do not re-prompt; add a missing capability/constraint to the repo and make Codex write it.
- The numbers that are safe to quote in a tutorial are the ones in the post itself (3→7 engineers, ~5 months, ~1M LOC, ~1,500 PRs, 3.5 PRs/engineer/day, ~100-line AGENTS.md, 6h+ runs, Friday 20% cleanup). Podcast numbers (1B tok/day, 5–10 PRs/day on GPT-5.2) should be attributed to the interview.

### Q2. Codex CLI harness mechanics (AGENTS.md layering, approvals/sandbox, hooks, skills, MCP, config.toml, sub-agents, compaction)

**Takeaway**
As of Oct 2026 the Codex harness is open source (github.com/openai/codex) and documented at developers.openai.com/codex (redirecting to learn.chatgpt.com/docs). It layers AGENTS.override.md/AGENTS.md from ~/.codex and root-to-cwd (32 KiB cap), runs the shell tool under an OS sandbox (Seatbelt / bwrap+seccomp / MXC) with `approval_policy` + `sandbox_mode`, and now ships lifecycle hooks (enabled by default, 12 events), skills (SKILL.md with progressive disclosure, 2%-of-context list budget), MCP servers, subagents (default/worker/explorer + TOML custom agents) and server-side compaction via `/responses/compact`.

**Cited Findings — the harness as a concept**
- OpenAI's own definition: the agent loop is "the core logic in Codex CLI that is responsible for orchestrating the interaction between the user, the model, and the tools the model invokes"; the harness "provides the core agent loop and execution logic that underlies all Codex experiences" (CLI, Cloud, VS Code). Loop: the model returns either a final assistant message or a tool call; the agent runs the tool, appends the output, re-queries; "each turn always ends with an assistant message." — ["Unrolling the Codex agent loop", OpenAI, 2026-01-23, Michael Bolin (date/author per search listing; not on proxied page)](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Prompt assembly (same post): `instructions` = `model_instructions_file` if set else the model's bundled `base_instructions`; the input list carries a sandbox developer message, optional `developer_instructions`, an aggregated "user instructions" message built from AGENTS.override.md/AGENTS.md found from the Git root down to cwd (32 KiB default), skills, and an environment message (cwd, shell). — [OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Sandbox scope: "the sandbox applies only to the Codex-provided shell tool. MCP tools must enforce their own guardrails." — [OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Prompt caching discipline: "Cache hits are only possible for exact prefix matches within a prompt"; Codex avoids changing tools/model/sandbox mid-conversation and instead appends new developer/user messages. Codex does not use `previous_response_id`, "primarily to keep requests fully stateless" for Zero Data Retention; reasoning survives via `encrypted_content`. — [OpenAI](https://openai.com/index/unrolling-the-codex-agent-loop/)
- Model + Harness + Surfaces: Gabriel Chua (OpenAI DevEx, APAC) wrote "Codex = Model + Harness + Surfaces", the harness being "the collection of instructions and tools", open source in openai/codex; "Codex models are trained in the presence of the harness" and tool use, execution loops, compaction and iterative verification "aren't bolted on behaviors". Simon Willison (2026-02-22) called this the first insider acknowledgement that the Codex model family is trained for the Codex harness, and noted Codex "is really a general agent harness disguised as a tool for programmers". — [Simon Willison, 2026-02-22](https://simonwillison.net/2026/Feb/22/how-i-think-about-codex/)

**Cited Findings — AGENTS.md discovery and layering**
- Order: (1) global `~/.codex` (or `$CODEX_HOME`): `AGENTS.override.md` if non-empty, else `AGENTS.md`; (2) project: from Git root down to cwd, at most one file per directory, checking `AGENTS.override.md`, then `AGENTS.md`, then names in `project_doc_fallback_filenames`; (3) concatenated root-down so "Files closer to the current directory appear later, so they override earlier guidance." Empty files skipped; stops at `project_doc_max_bytes` (32 KiB default). — [Codex docs: Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md) (→ learn.chatgpt.com/docs/agent-configuration/agents-md)
- Config knobs: `project_doc_fallback_filenames = ["TEAM_GUIDE.md", ".agents.md"]`, `project_doc_max_bytes = 65536`. — [Codex docs](https://developers.openai.com/codex/guides/agents-md)
- Recommended content: global file for "reusable working agreements" (e.g. "Always run `npm test` after modifying JavaScript files"); repo root for setup expectations ("documenting public utilities in `docs/`"); nested overrides for team rules; a `## Code Review Rules` section "in the AGENTS.md closest to the governed code". Best practices: "Place overrides as close as possible to the specialized work"; keep review rules concise and "Leave formatting and lint checks to CI"; split large instructions across nested directories rather than let guidance be truncated; use `AGENTS.override.md` for temporary changes. Verify with `codex --ask-for-approval never "Summarize the current instructions."` — [Codex docs](https://developers.openai.com/codex/guides/agents-md)
- Each AGENTS.md file is injected as its own user message under a header naming its directory (per the Codex prompting guide). — [OpenAI Cookbook, Codex prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-1-codex-max_prompting_guide)
- The agents.md standard: "a README for agents", used by "over 60k open-source projects", stewarded by the Agentic AI Foundation under the Linux Foundation, originated across OpenAI Codex, Amp, Jules, Cursor, Factory; precedence rule "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything"; "the main OpenAI repo has 88 such files". — [agents.md](https://agents.md/)
- OpenAI's internal usage guide: "Maintain an AGENTS.md file to help Codex operate more effectively in your repo" (naming conventions, business logic, known quirks); size tasks to "about an hour" / "a few hundred lines of code"; write prompts "like a GitHub issue"; plan in Ask mode first; fix recurring build errors in the environment config; best-of-N generations. — [OpenAI, "How OpenAI uses Codex" (undated, "research preview" era)](https://openai.com/business/guides-and-resources/how-openai-uses-codex/)

**Cited Findings — approvals and sandbox**
- `approval_policy`: `on-request` ("commands allowed by the sandbox can run without approval"; asks before leaving the sandbox or using ungranted network), `never` (`-a never`, works with every sandbox mode), or a `granular` table (`sandbox_approval`, `rules`, `mcp_elicitations`, `request_permissions`, `skill_approval`). `untrusted` is retired ("Codex and ChatGPT Work no longer support `approval_policy = "untrusted"`"), `on-failure` deprecated. — [Codex docs: Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security); [Config reference](https://developers.openai.com/codex/config-reference)
- `sandbox_mode`: `read-only`; `workspace-write` (default for version-controlled folders; "keeps network access turned off" unless `sandbox_workspace_write.network_access = true`); `danger-full-access` ("not recommended", via `--dangerously-bypass-approvals-and-sandbox` / `--yolo`). The "Auto" preset = `workspace-write` + `on-request`; `/permissions` switches modes. — [Codex docs](https://developers.openai.com/codex/agent-approvals-security)
- OS enforcement: macOS Seatbelt via `sandbox-exec`; Linux "uses `bwrap` plus `seccomp` by default" (Landlock only as a helper alias); Windows MXC; WSL2 uses the Linux path. "By default, the agent runs with network access turned off." Protected read-only paths inside writable roots: `.git`, `.agents`, `.codex`, `.aws`. — [Codex docs](https://developers.openai.com/codex/agent-approvals-security)
- Trust: project-local `.codex/config.toml`, hooks and agents load only for trusted projects (`projects.<path>.trust_level = "trusted"`). — [Config reference](https://developers.openai.com/codex/config-reference)

**Cited Findings — config.toml (key names)**
- Locations: `~/.codex/config.toml` user-level; `.codex/config.toml` project-level (trusted only); profiles as `$CODEX_HOME/<name>.config.toml` via `--profile`. — [Config reference](https://developers.openai.com/codex/config-reference); [Config sample](https://developers.openai.com/codex/config-sample)
- Model: `model`, `model_reasoning_effort`, `plan_mode_reasoning_effort`, `model_verbosity`, `review_model`, `model_provider`. Context: `model_context_window`, `model_auto_compact_token_limit`, `model_auto_compact_token_limit_scope` (`total` | `body_after_prefix`), `compact_prompt`. Instructions: `developer_instructions`, `model_instructions_file`, `project_doc_max_bytes`, `project_doc_fallback_filenames`, `project_root_markers`. Features: `features.multi_agent` (on by default), `features.hooks`, `features.memories` (off), `features.web_search`, `features.network_proxy`, etc. Skills: `skills.max_context_tokens` (default 2% of context window, cap 10,000), `skills.config`. Other: `notify` (command receiving a JSON payload), `web_search = disabled|cached|indexed|live`, `history.persistence`. — [Config reference](https://developers.openai.com/codex/config-reference)
- MCP: `mcp_servers.<id>` with `command`/`args`/`env`/`cwd` (stdio) or `url` (+ `bearer_token_env_var`, `http_headers`, OAuth `scopes`), lifecycle `enabled`/`required`/`startup_timeout_sec`/`tool_timeout_sec`, and per-tool `enabled_tools`/`disabled_tools`/`default_tools_approval_mode`/`tools.<tool>.approval_mode`/`tools.<tool>.output_token_limit`. — [Config reference](https://developers.openai.com/codex/config-reference)

**Cited Findings — hooks (exist as of Oct 2026, enabled by default)**
- "Hooks are enabled by default"; disable with `[features] hooks = false` (`codex_hooks` deprecated alias). Events: `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `UserPromptSubmit`, `SubagentStop`, `Stop`, `Interrupt`, `SessionStart`, `SubagentStart`, `SessionEnd`. — [Codex docs: Hooks](https://developers.openai.com/codex/hooks) (→ learn.chatgpt.com/docs/hooks)
- Where: `hooks.json` or inline `[hooks]` tables in config.toml at `~/.codex/` or `<repo>/.codex/` (trusted); all matching hooks from all layers run; plugins and enterprise `requirements.toml` can bundle hooks. Non-managed hooks must be reviewed/trusted via `/hooks` (trust bound to the hook's hash). — [Codex docs: Hooks](https://developers.openai.com/codex/hooks)
- Handler types `command` or `mcp_tool` (`prompt`/`agent` parsed but skipped); `matcher` regex on tool name (`Bash`, `apply_patch`, `Edit`, `Write`, `mcp__server__tool`), compaction trigger (`manual|auto`), session source (`startup|resume|clear|compact|fork`), or agent type; `timeout` default 600 s; `async = true` for background (≤8 concurrent); `additionalContextLimit` default 2,500 tokens. — [Codex docs: Hooks](https://developers.openai.com/codex/hooks)
- Input is one JSON object on stdin (`session_id`, `transcript_path`, `cwd`, `hook_event_name`, `model`, `turn_id`, `permission_mode`, plus `tool_name`/`tool_input`/`tool_response`, `prompt`, `agent_id`, `trigger`...). Output: exit 0 + JSON (`continue`, `stopReason`, `systemMessage`, `hookSpecificOutput`); exit 2 = block with stderr reason (PreToolUse, PostToolUse, UserPromptSubmit, SubagentStop, Stop). PreToolUse can `deny`, add `additionalContext`, or `allow` with `updatedInput`; Stop can `block` to force a continuation; PostCompact can inject context after compaction. — [Codex docs: Hooks](https://developers.openai.com/codex/hooks)
- Third-party timeline (UNVERIFIED against official changelog): `/hooks` browser and Pre/PostCompact hooks in CLI v0.129 (May 2026); subagents GA in v0.115.0 (March 16, 2026). — [codex.danielvaughan.com, 2026-05-07](https://codex.danielvaughan.com/2026/05/07/codex-cli-v0129-hooks-browser-compaction-hooks-runtime-management/); [same blog, 2026-03-27](https://codex.danielvaughan.com/2026/03/27/codex-cli-in-2026-whats-new/)

**Cited Findings — skills**
- A skill is a directory with a required `SKILL.md` carrying `name` and `description`, optional scripts/references/assets, and optional `agents/openai.yaml` (UI, invocation policy, tool deps). "Skills use progressive disclosure": Codex first sees only name/description/path and loads the full SKILL.md on selection. The initial list is capped at 2% of the context window (8,000 chars if unknown), raisable to 10,000 tokens via `skills.max_context_tokens`. — [Codex docs: Skills](https://developers.openai.com/codex/skills) (→ learn.chatgpt.com/docs/build-skills)
- Discovery: repo `.agents/skills` in each dir from cwd up to repo root; user `$HOME/.agents/skills`; admin `/etc/codex/skills`; system (bundled). Invocation: explicit `$skill` / `/skills` (or `@` in ChatGPT), or implicit when the task matches the description — "Because implicit matching depends on `description`, write concise descriptions with clear scope and boundaries." `allow_implicit_invocation: false` disables implicit use. Bundled: `$skill-creator`, `$skill-installer`; curated examples include Exec Plan, GitHub Fix CI, Linear, OpenAI Docs. — [Codex docs: Skills](https://developers.openai.com/codex/skills)

**Cited Findings — subagents**
- "Current Codex releases enable subagent workflows by default" (`agents.enabled = true`). Built-ins: `default`, `worker` (execution-focused), `explorer` (read-heavy). Custom agents are single TOML files in `~/.codex/agents/` or `.codex/agents/` with required `name`, `description`, `developer_instructions`, optional `model`/`model_reasoning_effort`/`model_verbosity`, and capability reductions (`features.shell_tool = false`, etc.). Not overridable per agent: `sandbox_mode`, `approval_policy`, `model_provider`, `mcp_servers`; "Subagents inherit the parent turn's current sandbox and approval settings". Concurrency via `agents.max_concurrent_threads_per_session`. The main thread "receives summaries rather than raw output"; `/subagents` inspects threads. — [Codex docs: Subagents](https://developers.openai.com/codex/subagents) (→ learn.chatgpt.com/docs/agent-configuration/subagents)

**Cited Findings — compaction**
- Early Codex used a manual `/compact` that produced a summary; now it calls the Responses API `/responses/compact` endpoint, which returns a `compaction` item with `encrypted_content` "that preserves the model's understanding of the conversation", automatically when `auto_compact_limit` is exceeded. — [OpenAI, Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)
- API-side guidance for your own harness: "Call `/responses/compact` when context grows, and keep the input within the model's window. Pass the returned compaction item into later requests." — [OpenAI Cookbook, Codex prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-1-codex-max_prompting_guide)

**Cited Findings — Codex cloud and app environments**
- Cloud task order: container created and repo checked out → setup script (+ optional maintenance script on cached-container resume) → internet access applied; setup scripts run with internet, the agent's own internet access is off by default with limited/unrestricted options. — [Codex docs: Cloud environments](https://developers.openai.com/codex/cloud/environments)
- Codex app local environments: setup steps live in a committed `.codex` folder; the setup script runs when the app creates a new git worktree per thread (worktrees don't inherit untracked files). — [Codex docs: Local environments](https://developers.openai.com/codex/app/local-environments)

**Inferences**
- The official docs' AGENTS.md guidance ("place overrides close to the code", "leave lint to CI", split instead of truncate) is the productized version of the blog post's "map, not manual" lesson.
- Hooks + `exit 2` blocking + PostToolUse `block` feedback are the generic mechanism a tutorial reader can use to reproduce "linters whose error messages tell the agent how to fix it" without writing a custom linter.
- Skills' 2%-of-context budget and the AGENTS.md 32 KiB cap are both hard numbers that make "context is a scarce resource" concrete.

**Gaps**
- I could not fetch the openai/codex GitHub README directly; the "open source harness" claim is from OpenAI's blog post and Chua/Willison.
- No official page documents nested-subagent depth limits or a version-by-version changelog for hooks/skills; the dates for those features rest on a third-party blog.

### Q3. OpenAI Agents SDK primitives and "A practical guide to building agents" (2025)

**Takeaway**
The Agents SDK (successor to Swarm) is deliberately minimal: agents, handoffs, guardrails, plus sessions and tracing as built-in features, with two stated design principles. The 2025 PDF guide recommends starting with a single agent and adding tools, splitting only on complex branching logic or overlapping tools, using manager (agents-as-tools) or decentralized (handoff) patterns, layering guardrails with optimistic parallel execution, and planning human intervention for failure thresholds and high-risk/irreversible actions.

**Cited Findings — Agents SDK**
- Primitives: Agents are "LLMs equipped with instructions and tools"; handoffs/agents-as-tools "allow agents to delegate to other agents for specific tasks"; guardrails "enable validation of agent inputs and outputs"; sessions = persistent memory layer across runs; tracing = built-in visualization/debugging/monitoring with hooks into OpenAI eval, fine-tuning and distillation tools. Design principles: "Enough features to be worth using, but few enough primitives to make it quick to learn." and "Works great out of the box, but you can customize exactly what happens." Agents have "a built-in loop that continues until the task is complete." Hello world: `Agent(name=..., instructions=...)` + `Runner.run_sync(agent, prompt)`. — [OpenAI Agents SDK docs](https://openai.github.io/openai-agents-python/)
- The SDK is "a production-ready successor to Swarm" and available in Python and TypeScript. — [OpenAI Agents SDK docs](https://openai.github.io/openai-agents-python/)

**Cited Findings — "A practical guide to building agents" (OpenAI PDF, 32 pages, 2025; no date printed in the text I extracted)**
- Definition: "Agents are systems that independently accomplish tasks on your behalf" (paraphrase of p.4; verbatim characteristics:) "It leverages an LLM to manage workflow execution and make decisions ... In case of failure, it can halt execution and transfer control back to the user." and "It has access to various tools ... always operating within clearly defined guardrails." "Applications that integrate LLMs but don't use them to control workflow execution—think simple chatbots, single-turn LLMs, or sentiment classifiers—are not agents." — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Three components: Model, Tools ("External functions or APIs the agent can use to take action"), Instructions ("Explicit guidelines and guardrails defining how the agent behaves"). Three tool types: Data (retrieve context), Action (send emails, update CRM, hand off a ticket), Orchestration ("Agents themselves can serve as tools for other agents"). — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Instruction best practices: "Use existing documents" (operating procedures → LLM-friendly routines), "Prompt agents to break down tasks", "Define clear actions" ("every step in your routine corresponds to a specific action or output"), "Capture edge cases". — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Single-agent first: "While it's tempting to immediately build a fully autonomous agent with complex architecture, customers typically achieve greater success with an incremental approach." "A single agent can handle many tasks by incrementally adding tools, keeping complexity manageable and simplifying evaluation and maintenance." "Our general recommendation is to maximize a single agent's capabilities first. More agents can provide intuitive separation of concepts, but can introduce additional complexity and overhead, so often a single agent with tools is sufficient." — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- When to split: "Complex logic: When prompts contain many conditional statements (multiple if-then-else branches)"; "Tool overload: The issue isn't solely the number of tools, but their similarity or overlap. Some implementations successfully manage more than 15 well-defined, distinct tools while others struggle with fewer than 10 overlapping tools." — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- The run loop: "Every orchestration approach needs the concept of a 'run', typically implemented as a loop that lets agents operate until an exit condition is reached. Common exit conditions include tool calls, a certain structured output, errors, or reaching a maximum number of turns." In the SDK, `Runner.run()` loops until a final-output tool is invoked or the model returns a response without tool calls. Prompt templates with policy variables are recommended to avoid premature multi-agent splits. — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Two multi-agent patterns: "Manager (agents as tools): A central 'manager' agent coordinates multiple specialized agents via tool calls"; "Decentralized (agents handing off to agents): Multiple agents operate as peers, handing off tasks to one another based on their specializations." — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Guardrails: "Think of guardrails as a layered defense mechanism. While a single one is unlikely to provide sufficient protection, using multiple, specialized guardrails together creates more resilient agents." Types: Relevance classifier, Safety classifier (jailbreaks/prompt injections), PII filter, Moderation, Tool safeguards ("Assess the risk of each tool ... pausing for guardrail checks before executing" high-risk actions), Rules-based protections (blocklists, input length limits, regex), Output validation. Build order: address known risks, "Add new guardrails based on real-world edge cases and failures you encounter", tune for security vs UX. — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Execution model: "The Agents SDK treats guardrails as first-class concepts, relying on optimistic execution by default. Under this approach, the primary agent proactively generates outputs while guardrails run concurrently, triggering exceptions if constraints are breached." — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- Human-in-the-loop: "Human intervention is a critical safeguard ... especially important early in deployment". "For a coding agent, this means handing control back to the user." Two triggers: "Exceeding failure thresholds: Set limits on agent retries or actions" and "High-risk actions: Actions that are sensitive, irreversible, or have high stakes should trigger human oversight until confidence in the agent's reliability grows. Examples include canceling user orders, authorizing large refunds, or making payments." — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)

**Inferences**
- The guide's "Instructions / Tools / Guardrails / Hooks" box around the single-agent loop is essentially a harness diagram; a tutorial can map Codex features onto it (AGENTS.md+skills = instructions, shell/apply_patch/MCP = tools, sandbox+approvals+hooks = guardrails, hooks = hooks).
- The guide's "escalate on failure thresholds and irreversible actions" matches the harness post's "Escalate to a human only when judgment is required".

**Gaps**
- The PDF text contains no publication date; "2025" (widely reported as April 2025) is from secondary coverage, UNVERIFIED in the document itself.
- I did not fetch the SDK's dedicated pages for handoffs/guardrails/sessions/tracing, so finer details (e.g. input guardrails only on the first agent, tracing export limits) are not confirmed here.

### Q4. Other OpenAI statements on harness vs model (prompting guides, Codex prompting guide, interviews)

**Takeaway**
OpenAI's prompting guides treat the harness/prompt as a first-class lever: the GPT-5 guide gives explicit recipes for dialing "agentic eagerness" up or down, for tool preambles, and shows a +4.3-point Tau-Bench gain just from persisting reasoning across tool calls; the Codex prompting guide tells harness builders to start from the Codex system prompt, strip planning/preamble instructions, use `apply_patch` and the terminal tool the model was trained on, and truncate tool output to ~10k tokens. OpenAI insiders state the Codex models are trained together with the harness.

**Cited Findings — GPT-5 prompting guide (OpenAI Cookbook, Aug 2025; page now marked archived)**
- Eagerness: "By default, GPT-5 is thorough and comprehensive when gathering context in an agentic environment." Less eager: lower `reasoning_effort` ("Many workflows can be accomplished with consistent results at medium or even low `reasoning_effort`"); a context-gathering spec starting "Goal: Get enough context fast. Parallelize discovery and stop as soon as you can act." with early-stop criteria ("You can name exact content to change", "Top hits converge (~70%) on one area/path") and a tool-call budget ("an absolute maximum of 2 tool calls"); escape hatch "even if it might not be fully correct". More eager: raise reasoning effort and a persistence prompt ("Never stop or hand back to the user when you encounter uncertainty"). — [OpenAI Cookbook, GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)
- Tool preambles: prompt "Always begin by rephrasing the user's goal in a friendly, clear, and concise manner, before calling any tools"; preambles improve the user's ability to follow long-running agent work. — [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)
- Harness effect measured: switching to the Responses API and passing `previous_response_id` so prior reasoning items are reused raised Tau-Bench Retail from 73.9% to 78.2% (same model). — [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)
- Instruction conflicts: GPT-5 "follows instructions precisely", so contradictory prompts cost reasoning tokens; the healthcare example fix adds "Do not do lookup in the emergency case, proceed immediately to providing 911 guidance." — [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)
- Cursor case study: set `verbosity` low globally but prompt "Write code for clarity first" for code; tell the model it "should almost never ask the user whether to proceed with a plan" because edits are reversible proposals; a "be THOROUGH" / `maximize_` instruction that worked for older models made GPT-5 over-search on small tasks and was softened; XML-structured spec sections improved adherence. — [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)
- Minimal reasoning advice: brief reasoning summaries, detailed tool preambles, disambiguated tool instructions, persistence reminders, explicit planning. — [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)

**Cited Findings — Codex prompting guide (OpenAI Cookbook; URL is the GPT-5.1-Codex-Max guide, page content now references `gpt-5.3-codex`; undated)**
- Start from the Codex starter prompt ("You are Codex, based on GPT-5" ... prefers `rg` over `grep`) rather than a GPT-5 prompt; remove instructions asking for an upfront plan, preambles or status updates during rollout because that "can cause the model to stop abruptly"; skip the plan tool for simple tasks; never end with only a plan. — [OpenAI Cookbook, Codex prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-1-codex-max_prompting_guide)
- Tools the model was trained on: use the exact `apply_patch` implementation, the shell tool with string commands and `workdir`, `update_plan` for TODOs; the model "was trained to excel at the `apply_patch` diff format and was primarily trained with a dedicated terminal tool"; dedicated tools mirroring terminal commands (e.g. a `git` tool) reduce terminal use; batch independent reads with `multi_tool_use.parallel`; truncate long tool output to about 10k tokens keeping head and tail. — [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-1-codex-max_prompting_guide)
- Reasoning effort: `medium` for interactive work, `high`/`xhigh` for the hardest long-running tasks. Anti-patterns: overthinking before first action, loggy status updates, re-reading/re-editing without progress, destructive git (`git reset --hard`). Before finishing mark every plan item Done/Blocked/Cancelled; avoid broad try/catch and silent fallbacks. — [OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-1-codex-max_prompting_guide)

**Cited Findings — insiders on model-vs-harness**
- "Codex models are trained in the presence of the harness"; tool use, execution loops, compaction and iterative verification "aren't bolted on behaviors" (Gabriel Chua, OpenAI DevEx, 2026-02-22, via Willison). — [Simon Willison](https://simonwillison.net/2026/Feb/22/how-i-think-about-codex/)
- Lopopolo (podcast): when the agent fails, ask "what capability, context, or structure is missing" rather than prompting harder; treat the model+agent as a black box and work the two external levers, context and tools (talk summary, secondary). — [Latent Space](https://latent.space/p/harness-eng); [Tessl talk outline (secondary)](https://tessl.io/registry/skills/github/jscraik/Agent-Skills/talk-lopopolo-harness-engineering)
- Greg Brockman X thread (Feb 2026), as quoted by a secondary source: maintain an AGENTS.md, make team tools agent-accessible via CLI or MCP server, "Write tests which are quick to run, and create high-quality interfaces between components." — [Artificial Ignorance, 2026-02-22](https://www.ignorance.ai/p/the-emerging-harness-engineering) (UNVERIFIED: original thread not fetched)

**Inferences**
- The Codex guide's "remove planning/preamble instructions" directly contradicts the general GPT-5 guide's preamble advice; the tutorial should say the right harness prompt depends on which model family is in the loop.
- The Tau-Bench +4.3 and the "trained in the presence of the harness" statement together support the tutorial's claim that harness choices are not cosmetic.

**Gaps**
- No GPT-5-Codex or GPT-5.x system-card passage explicitly discussing scaffold design was found beyond the SWE-bench setup notes in Q5; Codex-team podcasts other than Latent Space were not reviewed.
- The GPT-5 prompting guide page shows no date; "Aug 2025" is from the launch timing (secondary PDF mirror dated 2025-08). UNVERIFIED on page.

### Q5. Public numbers showing OpenAI benchmark scores depend on harness/scaffold

**Takeaway**
OpenAI's own system cards disclose that SWE-bench Verified numbers are produced with an "internal tool scaffold" (bash + `apply_patch`) on a 477-task subset, that o1 had to be run under the open-source Agentless scaffold because it lacked tools, and that prompt-level settings (verbosity) move the score; the only OpenAI-published same-model harness delta I found is +4.3 points on Tau-Bench from reasoning persistence. Independent SWE-bench runs of GPT-5-Codex (69.4% on Vals.ai vs 74.5% vendor) illustrate the harness gap but are not controlled ablations.

**Cited Findings**
- GPT-5 System Card, SWE-bench Verified: "We use an internal tool scaffold that provides access to bash commands and the apply_patch tool"; "a fixed subset of n=477 verified tasks which have been validated on our internal infrastructure"; "we average over 4 tries per instance to compute pass@1"; "Changes in verbosity can lead to variation in eval performance"; the launch-blog 74.9% used default (medium) API verbosity rather than the system card's trained-in maximum. — [GPT-5 System Card (arXiv 2601.03267)](https://arxiv.org/html/2601.03267v2)
- gpt-oss model card (same OpenAI eval setup for o3/o4-mini): "an internal tool scaffold designed for efficient iterative file editing and debugging", 477-task subset. — [gpt-oss model card (arXiv 2508.10925), per search summary](https://arxiv.org/pdf/2508.10925)
- o1 System Card: because o1 lacked code execution/file-editing tools, OpenAI used the open-source Agentless scaffold, "the best one available at the time". — [o1 System Card (arXiv 2412.16720), per search summary](https://arxiv.org/pdf/2412.16720)
- Same-model harness delta: Tau-Bench Retail 73.9% → 78.2% from Responses API reasoning persistence (`previous_response_id`). — [OpenAI Cookbook, GPT-5 prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_prompting_guide)
- GPT-5-Codex launch figure 74.5% SWE-bench Verified (refactoring 51.3% vs 33.9% for GPT-5) per OpenAI's announcement as reported by TechRadar; Vals.ai's standardized harness measured 69.4%. — [TechRadar](https://www.techradar.com/pro/openai-launches-gpt-5-codex-with-a-74-5-percent-success-rate-on-real-world-coding); [Vals.ai](https://www.vals.ai/benchmarks/swebench)
- A 2026 survey states the scaffold (prompt construction, tool set, output parsing, context management, retry logic) "can move a SWE-bench score by 10-20 points on identical model weights" and that vendor-reported scores "should not be interpreted as controlled ablations against open-source harnesses". — [arXiv 2606.20683 survey, per search summary](https://arxiv.org/pdf/2606.20683)

**Inferences**
- OpenAI's disclosed practice (own scaffold, own task subset, verbosity caveat) is itself an admission that scaffold is part of the measured system; a tutorial can use "same weights, different harness, different score" with the Tau-Bench number as the one OpenAI-authored controlled example.

**Gaps**
- I did not find GPT-5-Codex, GPT-5.1/5.2 or later system-card text explicitly quantifying scaffold sensitivity; the 10–20 point figure is from an independent survey (summary only, not the paper text).
- The GPT-5-Codex system card itself was not fetched; its scaffold description is UNVERIFIED here.
