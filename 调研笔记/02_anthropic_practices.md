### Q0. Anthropic's own definition of "harness" and the foundational framing (2024-2025)

**Takeaway**
Anthropic defines the harness as "the layer around the model that provides the tools and manages the context the model sees", and frames every agent as the same three-phase loop: gather context, take action, verify results. The 2024 "Building effective agents" post supplies the vocabulary (workflows vs agents, augmented LLM, five workflow patterns, agent-computer interface) that all later harness posts build on.

**Cited Findings**
- Official definition: "Claude Code is the layer around the model that provides the tools and manages the context the model sees. This surrounding layer is what the term agentic harness refers to." — [How Claude Code works, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/how-claude-code-works)
- The loop: "When you give Claude a task, it works through three phases: gather context, take action, and verify results. These phases blend together." and "Each tool use gives Claude new information that informs the next step. This is the agentic loop in action." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- The evals post defines the agent harness as the thing being evaluated alongside the model: "Agent harness (scaffold): The system that lets a model act as an agent. 'Evaluating an agent' means evaluating the harness and model together." — [Demystifying evals for AI agents, official blog, 2026-01-09](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Workflows vs agents (Dec 2024): workflows are "systems where LLMs and tools are orchestrated through predefined code paths"; agents are systems where LLMs dynamically direct their own processes and tool usage. Agents are "typically just LLMs using tools based on environmental feedback in a loop." — [Building effective agents, official blog, 2024-12-19](https://www.anthropic.com/engineering/building-effective-agents)
- Building block: "an LLM enhanced with augmentations such as retrieval, tools, and memory" (the "augmented LLM"). Five workflow patterns: prompt chaining, routing, parallelization (sectioning and voting), orchestrator-workers, evaluator-optimizer ("one LLM call generates a response while another provides evaluation and feedback in a loop"). — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Three core principles: maintain simplicity; prioritize transparency by explicitly showing planning steps; "Carefully craft your agent-computer interface (ACI) through thorough tool documentation and testing." — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Tool-engineering appendix: "Poka-yoke your tools. Change the arguments so that it is harder to make mistakes."; the SWE-bench agent erred with relative paths, so the team "changed the tool to always require absolute filepaths"; "we actually spent more time optimizing our tools than the overall prompt." — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- The March 2026 harness post cites this guidance back: "find the simplest solution possible, and only increase complexity when needed". — [Harness design for long-running application development, official blog, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- The Agent SDK post states that "the agent harness behind Claude Code now powers most of Anthropic's major agent loops" and that the key design principle is to give agents a computer so they can work the way humans do. — [Building agents with the Claude Agent SDK, official blog, 2025-09-29](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)

**Inferences**
- Anthropic's posts converge on one mental model a beginner can hold: harness = loop + tools + context management + verification + guardrails, with the model doing the reasoning. Everything in Q1 is a concrete feature that plugs into one of those slots.

**Gaps**
- None material for this question.

### Q1. Claude Code as a harness: building blocks and the problem each solves

**Takeaway**
Claude Code's harness is a thin loop plus a feature layer. The docs organize the features by *when they load into context* (always-on CLAUDE.md; on-demand skills/MCP; isolated subagents; zero-context hooks) and by *what they enforce* (permission modes, sandboxing, hooks are enforcement; CLAUDE.md and skills are advisory). The single constraint behind most design choices is the context window: "the context window is the most important resource to manage."

**Cited Findings**

*The agent loop and built-in tools*
- Built-in tool categories: file operations (Read, Edit, Write), search (Glob, Grep), execution (Bash), web (WebSearch, WebFetch), discovery (ToolSearch: "Dynamically find and load tools on-demand instead of preloading all of them"), orchestration (Agent, Skill, AskUserQuestion, TaskCreate, TaskUpdate). — [Agent SDK: How the agent loop works, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Parallelism rule: "Read-only tools (like Read, Glob, Grep, and MCP tools marked as read-only) can run concurrently. Tools that modify state (like Edit, Write, and Bash) run sequentially to avoid conflicts." Custom tools default to sequential unless `readOnlyHint` is set. — [Agent loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Example loop for "fix the failing tests": run suite, read errors, search for files, read them, edit, re-run tests. — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Per-tool output cap: "For Claude Code, we restrict tool responses to 25,000 tokens by default." — [Writing effective tools for agents, official blog, 2025-09-11](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Sessions are persisted as JSONL: "Each message, tool use, and result is written to a plaintext JSONL file under ~/.claude/projects/, which enables rewinding, resuming, and forking sessions." Resume keeps the session ID; fork (`--fork-session` / `/branch`) copies history into a new ID. — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Checkpoints: "Before Claude edits a file, it snapshots the current contents." They "only cover file changes" and remote effects "can't be checkpointed. You control those with your permission mode and permission rules." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- System reminders: Claude Code injects its own context (CLAUDE.md, output-style instructions, "A note when a file Claude read earlier changes on disk", commit/PR attribution lines). — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)

*Context compaction / auto-compact*
- "Claude Code manages context automatically as you approach the limit. It clears older tool outputs first, then summarizes the conversation if needed. Your requests and key code snippets are preserved; detailed instructions from early in the conversation may be lost. Put persistent rules in CLAUDE.md rather than relying on conversation history." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Thrash guard: "If a single file or tool output is so large that context refills immediately after each summary, Claude Code stops auto-compacting after a few attempts and shows an error instead of looping." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Controls: `/compact <instructions>`, a "Compact Instructions" section in CLAUDE.md, partial compaction from the rewind menu ("Summarize from here" / "Summarize up to here"), `/btw` for side questions that never enter history, `/context` to see what uses space. — [Best practices, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/best-practices)
- Internals as described in the context-engineering post: compaction "preserves architectural decisions, unresolved bugs, and implementation details, and discards redundant tool outputs. The agent then continues with the summary plus the five most recently accessed files." — [Effective context engineering, official blog, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- After compaction, skills are re-attached: "Claude Code re-attaches the most recent invocation of each skill after the summary, keeping the first 5,000 tokens of each. Re-attached skills share a combined budget of 25,000 tokens." — [Skills, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/skills)
- SDK view: compaction emits a `compact_boundary` system message; `PreCompact` hook can archive the full transcript; CLAUDE.md is re-injected on every request so "Persistent rules belong in CLAUDE.md ... rather than in the initial prompt". — [Agent loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)

*CLAUDE.md project memory (and auto memory)*
- Two memory systems: CLAUDE.md (you write; instructions and rules; loaded every session) and auto memory (Claude writes; learnings; "Every session (first 200 lines or 25KB)"). Both are "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." — [How Claude remembers your project, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/memory)
- Locations: managed/org CLAUDE.md; `~/.claude/CLAUDE.md` (user); `./CLAUDE.md` or `./.claude/CLAUDE.md` (project, shared via source control); `./CLAUDE.local.md` (gitignored personal). Files above the working directory load at launch; "Files in subdirectories load on demand" (when Claude reads/edits a file there). All discovered files are concatenated, root-to-cwd order. — [Memory docs](https://code.claude.com/docs/en/memory)
- `@path/to/import` imports, relative to the containing file, max depth four hops; external imports (outside the working dir) trigger a one-time approval dialog. — [Memory docs](https://code.claude.com/docs/en/memory)
- `.claude/rules/` directory: topic files, discovered recursively, with optional `paths:` frontmatter so a rule "only load[s] into context when Claude works with matching files"; `~/.claude/rules/` for user-level rules. — [Memory docs](https://code.claude.com/docs/en/memory)
- AGENTS.md is read in place of CLAUDE.md when no CLAUDE.md exists in or above cwd (v2.1.277+). — [Memory docs](https://code.claude.com/docs/en/memory)
- Size guidance: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." `/init` generates a starter; `/doctor` proposes cuts. — [Memory docs](https://code.claude.com/docs/en/memory); same 200-line rule in [Extend Claude Code, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/features-overview)
- Include/exclude table: include "Bash commands Claude can't guess", "Code style rules that differ from defaults", testing instructions, repo etiquette, architecture decisions, env quirks, gotchas; exclude "Anything Claude can figure out by reading code", standard conventions, detailed API docs, frequently changing info, tutorials, file-by-file descriptions. Test: "Would removing this cause Claude to make mistakes?" and "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" — [Best practices](https://code.claude.com/docs/en/best-practices)

*Permission modes, sandboxing, auto mode*
- Mode table: `default` (Manual) runs "Reads only" without asking; `acceptEdits` runs reads, file edits, and `mkdir/touch/mv/cp` etc.; `plan` runs "Reads, plus classifier-approved commands when auto mode is available"; `auto` runs "Everything, with background safety checks"; `dontAsk` runs pre-approved tools and denies "anything that would prompt" ("Locked-down CI and scripts"); `bypassPermissions` runs "Everything" ("Isolated containers and VMs only"). — [Permission modes, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/permission-modes)
- Plan mode: "Plan mode tells Claude to research and propose changes without making them. Claude reads files, runs shell commands to explore, and writes a plan, but does not edit your source." Enter via `Shift+Tab`, `/plan`, or `claude --permission-mode plan`; `Ctrl+G` opens the plan in an editor; plan files live in `~/.claude/plans/`. — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Auto mode: "A separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or appears driven by hostile content Claude read." Fallback: "if the classifier blocks an action 3 times in a row or 20 times total, auto mode pauses and Claude Code resumes prompting." Classifier sees user messages, non-read-only tool calls, CLAUDE.md; "Tool results are stripped from those requests, so hostile content in a file or web page can't manipulate the classifier directly." Default classifier: Claude Sonnet 5. Built-in starting mode from v2.1.283. — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Why auto mode exists: manual prompts cause approval fatigue and "in practice users accept 93% of them anyway." Design: two stages (fast yes/no filter tuned to "err on the side of blocking", then chain-of-thought on flagged actions); >20 block rules in four groups (destroy or exfiltrate, degrade security posture, cross trust boundaries, bypass review or affect others). Eval: real traffic n=10,000, FPR 8.5% stage-1-only vs 0.4% full pipeline; real overeager actions n=52, FNR 17% full pipeline ("the honest number"); synthetic exfiltration n=1,000, FNR 5.7%. — [How we built Claude Code auto mode, official blog, 2026-03-25](https://www.anthropic.com/engineering/claude-code-auto-mode)
- Sandboxing: filesystem isolation (read/write only in cwd) plus network isolation (traffic only via a Unix socket to a proxy outside the sandbox that confirms new domains), enforced by Linux bubblewrap and macOS seatbelt, applying to subprocesses too. "Without network isolation, a compromised agent could exfiltrate sensitive files like SSH keys." Internal usage: sandboxing "safely reduces permission prompts by 84%." Open-sourced at github.com/anthropic-experimental/sandbox-runtime. — [Beyond permission prompts, official blog, 2025-10-20](https://www.anthropic.com/engineering/claude-code-sandboxing)
- Protected paths (`.git`, `.claude`, `.bashrc`, `.mcp.json`, etc.) are never auto-approved except in bypass mode. — [Permission modes](https://code.claude.com/docs/en/permission-modes)

*Hooks*
- Definition: "Hooks are user-defined shell commands, HTTP endpoints, MCP tool calls, LLM prompts, or subagents that execute automatically at specific points in Claude Code's lifecycle." Five handler types: command, http, mcp_tool, prompt, agent (experimental). — [Hooks reference, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/hooks)
- Events: SessionStart, SessionEnd, UserPromptSubmit, Stop, StopFailure, PreToolUse ("Before a tool call executes. Can block it"), PostToolUse, PostToolUseFailure, PermissionRequest, Notification, SubagentStart, SubagentStop, PreCompact, TaskCreated, TaskCompleted, ConfigChange, FileChanged, WorktreeCreate/Remove, Elicitation. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Control protocol: exit 0 = proceed (JSON on stdout can still allow/deny); exit 2 = block, "the message that comes with the block is your hook's stderr"; other exit codes = non-blocking error. PreToolUse JSON `permissionDecision` takes allow/deny/ask/defer; a Stop hook can "prevent Claude from stopping, which continues the conversation." — [Hooks reference](https://code.claude.com/docs/en/hooks)
- Problem solved: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." and "Put guardrails in hooks. An instruction like 'never edit .env' in CLAUDE.md or a skill is a request, not a guarantee. A PreToolUse hook that blocks the edit is enforcement." Context cost: "Zero, unless hook returns additional context". — [Best practices](https://code.claude.com/docs/en/best-practices); [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Config locations merge across `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json`, managed policy, plugin `hooks/hooks.json`, skill/subagent frontmatter. — [Hooks reference](https://code.claude.com/docs/en/hooks)

*Slash commands and skills*
- "Custom commands have been merged into skills. A file at .claude/commands/deploy.md and a skill at .claude/skills/deploy/SKILL.md both create /deploy and work the same way." — [Skills docs](https://code.claude.com/docs/en/skills)
- Progressive disclosure: "In a regular session, skill descriptions are loaded into context so Claude knows what's available, but full skill content only loads when invoked." Description (plus `when_to_use`) is "truncated at 1,536 characters in the skill listing." Keep SKILL.md under 500 lines; move reference material to separate files. — [Skills docs](https://code.claude.com/docs/en/skills)
- Frontmatter: `name`, `description`, `disable-model-invocation` (user-only; "You don't want Claude deciding to deploy because your code looks ready"), `user-invocable: false` (Claude-only), `allowed-tools`, `context: fork` (run in a forked subagent), `agent`, `model`, `effort`, `paths`, `hooks`. Dynamic context injection with `` !`git diff HEAD` ``. Arguments via `$ARGUMENTS`, `$0`, named args. — [Skills docs](https://code.claude.com/docs/en/skills)
- Engineering-blog origin: Skills are "organized folders of instructions, scripts, and resources that agents can discover and load dynamically"; three disclosure levels (metadata in system prompt; SKILL.md body; bundled files); bundled scripts can be executed without loading them into context; Agent Skills became an open standard 2025-12-18. — [Equipping agents for the real world with Agent Skills, official blog, 2025-10-16](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

*Subagents*
- "Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions." "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history ... Only the summary returns to the main conversation." Exception: a *fork* inherits the parent conversation. — [Subagents, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/sub-agents)
- Defined as Markdown + YAML (`name`, `description`, `tools`, `model`, `permissionMode`, `isolation: worktree`, `skills`, `omitClaudeMd`); scopes `.claude/agents/`, `~/.claude/agents/`, plugins, `--agents` flag. Built-ins: Explore (read-only, fast), Plan (read-only research during plan mode), general-purpose. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Limits: 20 concurrent by default (`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`); nesting up to three layers; combined descriptions over 15,000 tokens trigger a warning; background subagents "run with a smaller built-in tool set"; `AskUserQuestion`, `EnterPlanMode`, `ExitPlanMode`, `Workflow` are always removed. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Benefits list: preserve context, enforce constraints, reuse configurations, specialize behavior, control costs ("routing tasks to faster, lower-cost models like Haiku"). — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Dynamic workflows (June 2026): Claude writes a JavaScript file using `agent(prompt, opts)`, `parallel()`, `pipeline()` to orchestrate many subagents; built to counter "agentic laziness" (e.g. "addressing 35 of the 50 items in a security review"), "self-preferential bias", and "goal drift". Dashboard examples: review-changes 14 agents / 482k tokens / 6m12s; deep-research 22 agents / 1.1M tokens / 11m03s. "parallelism and specialization have to earn their coordination cost." — [A harness for every task: dynamic workflows, official blog, 2026-06-02](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)

*MCP*
- "Claude Code can connect to hundreds of external tools and data sources through the Model Context Protocol (MCP)". Transports: HTTP (recommended), SSE (deprecated), stdio, WebSocket. Scopes local / project (`.mcp.json`, needs approval) / user. — [MCP, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/mcp)
- Context control: "MCP tool definitions are deferred by default and loaded on demand via tool search, so only tool names and server instructions consume context until Claude uses a specific tool." — [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)
- Output limits: "Claude Code displays a warning when MCP tool output exceeds 10,000 tokens and limits output to 25,000 tokens by default" (`MAX_MCP_OUTPUT_TOKENS`); text results over 50,000 characters are saved to a file. — [MCP docs](https://code.claude.com/docs/en/mcp)
- Security: "Verify you trust each server before connecting it. Servers that fetch external content can expose you to prompt injection risk." — [MCP docs](https://code.claude.com/docs/en/mcp)

*Worktrees and parallel sessions*
- `claude --worktree <name>` creates `.claude/worktrees/<name>/` on branch `worktree-<name>`; "one session can build a feature while a second fixes a bug." Claude can call `EnterWorktree`; subagents can set `isolation: worktree`; `/batch` splits a change "across 5 to 30 subagents. Each subagent works in its own worktree." — [Worktrees, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/worktrees); [Best practices](https://code.claude.com/docs/en/best-practices)
- Isolation enforcement: four checks block edits to the main checkout, commands whose cwd is the main checkout, git redirects into it, and unparseable command shapes. Clean unnamed worktrees are auto-removed on exit; `.worktreeinclude` copies gitignored files like `.env`. — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Other parallel options: cross-session messaging, desktop app sessions, cloud, Agent view (`claude agents`), Agent teams (experimental). — [Best practices](https://code.claude.com/docs/en/best-practices)

*Background tasks*
- "When Claude Code runs a command in the background, it runs the command asynchronously and immediately returns a background task ID." Trigger by prompt or `Ctrl+B`; a foreground command that hits its timeout is auto-moved to background (unless it starts with `sleep`); `/tasks` lists running shells and subagents; tasks are killed at exit or above 5GB output. — [Interactive mode, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/interactive-mode)
- Queued messages: a message typed while Claude works is passed "as soon as those tool calls finish, within the same turn". — [Interactive mode](https://code.claude.com/docs/en/interactive-mode)

*Context-cost table and when-to-use rules*
- Context cost by feature: CLAUDE.md = every request; skills = descriptions every request, body when used; MCP = tool names only until used; subagents = isolated; hooks = zero unless they return output. — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Trigger table: "Claude gets a convention or command wrong twice → Add it to CLAUDE.md"; "You paste the same playbook ... for the third time → Capture it as a skill"; "A side task floods your conversation with output ... → Route it through a subagent"; "You want something to happen every time without asking → Write a hook"; "A second repository needs the same setup → Package it as a plugin". — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Skill vs subagent: "Skills are reusable content you can load into any context"; "Subagents are isolated workers that run separately". Hook vs skill: hook "Fires on its event without Claude deciding"; skill "Claude interprets the instructions; outcome can vary". — [Extend Claude Code](https://code.claude.com/docs/en/features-overview)
- Steering blog (Jun 2026): "Keep CLAUDE.md under 200 lines, give it an owner, and review changes to it like code."; "Use hooks for anything that should happen deterministically." — [Steering Claude Code, official blog, 2026-06-18](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)

**Inferences**
- The design pattern a tutorial can teach: separate *advice* (CLAUDE.md, skills, prompts) from *enforcement* (hooks, permission rules, sandbox, worktree isolation), and separate *always-loaded* from *just-in-time* context. Every Claude Code feature sits in one cell of that 2x2.
- Numeric budgets worth memorizing for harness builders: 25k-token tool-output cap, 10k/25k MCP output warn/limit, 200-line CLAUDE.md, 500-line SKILL.md, 1,536-char skill description, 5k/25k skill re-attach after compaction, 20 concurrent subagents, 3-deep nesting, 3-consecutive / 20-total classifier denials.

**Gaps**
- The hooks, sub-agents, skills, MCP and permission-modes doc pages were only read to their first 100k characters; later sections (resume semantics, full MCP tool-search thresholds, `/mcp__` prompt syntax) were not captured.
- The docs do not publish the exact compaction trigger threshold (percentage of context) or the full compaction prompt.

### Q2. Claude Agent SDK: what it exposes and the gather → act → verify loop

**Takeaway**
The Agent SDK is Claude Code as a library (Python and TypeScript, bundling the Claude Code binary): the same tools, loop, permissions, hooks, subagents, MCP, sessions, skills and compaction. The September 2025 post that renamed it from "Claude Code SDK" prescribes designing every agent around gather context → take action → verify work, and names the specific mechanisms for each phase.

**Cited Findings**
- Rename: "we're renaming the Claude Code SDK to the Claude Agent SDK" because teams used it for non-coding work; "the agent harness behind Claude Code now powers most of Anthropic's major agent loops." — [Building agents with the Claude Agent SDK, official blog, 2025-09-29](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- What the SDK is: "The Agent SDK gives you the same tools, agent loop, and context management that power Claude Code, programmable in Python and TypeScript." Capability table: built-in tools, hooks, subagents, MCP, permissions, sessions, skills/commands/memory (loaded from `.claude/` and `~/.claude/`), plugins. Positioned against the CLI, the Client SDK ("You write the tool loop yourself"), and Managed Agents ("A hosted agent harness"). — [Agent SDK overview, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/agent-sdk/overview)
- Loop mechanics: receive prompt → evaluate and respond → execute tools (hooks can intercept) → repeat ("Each full cycle is one turn ... until it produces a response with no tool calls") → return `ResultMessage` with text, usage, cost, session ID. Controls: `max_turns`/`maxTurns` (tool-use turns only), `max_budget_usd`, `effort` (low/medium/high/xhigh/max), `permission_mode`, `allowed_tools`, `disallowed_tools`, `canUseTool` callback. Result subtypes: `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`, `error_max_structured_output_retries`. "Setting a budget is a good default for production agents." — [Agent loop docs](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Gather context mechanisms: agentic search ("The file system represents information that could be loaded into context"; grep/tail to load selectively; "The folder structure becomes a form of context engineering"); semantic search ("Faster than agentic search but less accurate, harder to maintain, and less transparent" — start with agentic search, add semantic only if needed); subagents ("each subagent has its own context window and returns only relevant information"); compaction. — [Agent SDK post](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- Take action mechanisms: tools ("Tool descriptions are prominent in Claude's context, so design them for context efficiency"); bash and scripts (e.g. download a PDF, convert to text, search); code generation ("Code is precise, composable, and reusable" — claude.ai file creation uses generated Python for xlsx/pptx/docx); MCP (handles auth and API calls). — [Agent SDK post](https://claude.com/blog/building-agents-with-the-claude-agent-sdk)
- Verify work mechanisms: rules-based feedback (linting; "generating TypeScript and linting it gives more feedback layers than plain JavaScript"); visual feedback (screenshots, Playwright MCP, multiple viewports; one screenshot has limited viewport information); LLM-as-judge (called "generally not very robust" with latency tradeoffs, use where extra performance justifies cost). ### Q3. "Effective harnesses for long-running agents" (Nov 26, 2025): the exact design and what it fixed

**Takeaway**
Two prompts, one harness: an *initializer* session writes `init.sh`, `claude-progress.txt`, a JSON feature list (200+ entries, all `passes: false`) and the first git commit; every later *coding* session reads git log + progress file, picks the highest-priority failing feature, starts the app via `init.sh`, runs an end-to-end test, implements one feature, self-verifies with browser automation, commits and updates the progress file. This replaced "one-shot everything" and "declare victory early" behaviour.

**Cited Findings**
- Motivation: sessions "start with no memory of earlier ones", compared to engineers working shifts with no handoff. Compaction alone was insufficient: even Opus 4.5 given "build a clone of claude.ai" either "tried to one-shot the app and ran out of context mid-implementation, leaving half-built, undocumented features" or "saw progress, declared the job done, and stopped early." — [Effective harnesses for long-running agents, official blog, 2025-11-26](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Initializer outputs: `init.sh`, `claude-progress.txt`, an initial git commit, and a feature-list JSON with fields `category`, `description`, `steps`, `passes`. "over 200 features", all initially failing. JSON chosen "because the model is less likely to inappropriately change or overwrite it than Markdown." — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Coding-session startup routine: run `pwd`, read git log and progress file, read the feature list and pick the highest-priority unfinished feature, start the dev server via `init.sh`, run a basic end-to-end test before new work. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- One feature per session, "critical" to curbing the tendency to do too much at once; commit with descriptive messages; git lets it revert bad changes. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Clean-state principle: leave code "that would be appropriate for merging to a main branch". — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Protected artifacts, strong wording: "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Testing like a user: without explicit prompting Claude tested only with unit tests or `curl`; the harness used the Puppeteer MCP server for browser testing; known gap: it cannot see browser-native alert modals, so such features were buggier. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Failure→fix table: premature victory → structured feature list + self-verify before marking passing; bugs/undocumented progress → git repo + progress notes read at start, committed at end; marking done without testing → self-verification; wasted time figuring out how to run the app → `init.sh`. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Footnote: the two "agents" differ only in their initial user prompt; system prompt, tools and harness are identical. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Open questions named: single general agent vs specialized testing/QA/cleanup agents; generalizing beyond web apps. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Independent corroboration of the same pattern at larger scale (Feb 2026, C compiler): a bash `while true` loop restarting fresh Claude Code sessions with a prompt file; 16 agents in Docker containers sharing a bare git repo; task locking via files in `current_tasks/` ("If two agents try to claim the same task, git's synchronization forces the second agent to pick a different one"); no orchestrator; tests print few lines with "ERROR" on the same line for grep; `--fast` 1%/10% sample; extensive READMEs and progress files because agents start with no context. Numbers: ~2,000 sessions, ~2 weeks, ~2B input / 140M output tokens, just under $20,000, ~100,000 lines of Rust, ~99% pass on compiler suites. Failures: late regressions (fixed by CI gating), all agents hitting the same kernel bug (fixed by using GCC as an oracle to split work), one agent ran `pkill -9 bash`. Quote: "For autonomous systems, it is easy to see tests pass and assume the job is done, when this is rarely the case." — [Building a C compiler with a team of parallel Claudes, official blog, 2026-02-05](https://www.anthropic.com/engineering/building-c-compiler)

**Inferences**
- The harness is almost entirely *files + git + a startup ritual*; no custom code was needed. This is the cheapest harness pattern to teach first.
- The JSON-over-Markdown choice and the "unacceptable to edit tests" sentence are both examples of designing against known model tendencies (overwriting state, gaming verification).

**Gaps**
- The post gives no quantitative results (session counts, hours, pass rate before/after). The caller should not invent them.
- The exact initializer and coding prompts are not reproduced in full in the fetched text.

### Q4. "Effective context engineering for AI agents" (Sep 29, 2025): techniques

**Takeaway**
Treat context as "a finite resource with diminishing marginal returns" and aim for "the smallest possible set of high-signal tokens". Four long-horizon techniques: compaction, structured note-taking (agentic memory), sub-agent architectures, and just-in-time retrieval, plus rules for system prompts ("right altitude"), tools, and examples.

**Cited Findings**
- Definition: context engineering is "curating all tokens present during inference, including tools, external data, and message history"; the core question is "what configuration of context is most likely to generate our model's desired behavior?" — [Effective context engineering for AI agents, official blog, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Context rot: recall falls as token count grows, gradually, in all models; the "attention budget" is drawn down by every token; cause is n² pairwise attention plus scarce long-sequence training data. — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- System prompts: "right altitude" between brittle if-else logic and vague guidance; "Minimal does not mean short"; start minimal on the best model and add instructions from observed failures; organize with XML tags or Markdown headers. — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Tools: "self-contained, robust to errors, have minimal overlap in functionality, and have clear, unambiguous parameters"; "If a human engineer cannot say which tool to use, the agent will likely struggle too." — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Examples: curate "a small set of diverse, canonical examples" rather than lists of edge-case rules. — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Just-in-time retrieval: keep lightweight identifiers (paths, queries, links) and load at runtime; Claude Code uses `head`/`tail` on large data; metadata (paths, names, timestamps) is signal (`tests/test_utils.py` vs `src/core_logic/test_utils.py`); trade-off is slower runtime exploration. Hybrid: Claude Code "drops CLAUDE.md files into context at the start and uses glob and grep for just-in-time retrieval"; "do the simplest thing that works." — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Compaction: summarize and restart; tune by "first maximize recall, then improve precision"; lightest form is clearing old tool results (shipped on the Developer Platform). — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Structured note-taking: notes persisted outside the window (Claude Code to-do lists; a `NOTES.md`); Claude-plays-Pokémon kept progress across thousands of steps (e.g. Pikachu +8 levels toward 10 over 1,234 steps) and resumed after resets; a memory tool shipped in public beta with Sonnet 4.5. — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Sub-agents: a sub-agent may use "tens of thousands of tokens or more" but returns a condensed summary, "often 1,000–2,000 tokens". — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Choosing: compaction for long back-and-forth; note-taking for iterative development with milestones; multi-agent for complex research with parallel exploration. — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Managed Agents (Apr 2026) externalizes this: the session is "an append-only log" outside the model's window, read via `getEvents()` positional slices, "so nothing is lost to irreversible compaction or trimming"; the harness decides how events are transformed before entering the window. Three virtualized components: session, harness ("the loop that calls Claude and routes its tool calls"), sandbox; tool execution via `execute(name, input) → string`; crash recovery via `wake(sessionId)` + `getSession(id)`; p50 TTFT cut ~60%, p95 >90% by lazy container provisioning. — [Scaling Managed Agents: Decoupling the brain from the hands, official blog, 2026-04-08](https://www.anthropic.com/engineering/managed-agents)

**Inferences**
- Claude Code's product features map one-to-one onto this post: auto-compact = compaction; auto memory, TodoWrite/TaskCreate and progress files = note-taking; Agent tool / Explore = sub-agents; Glob/Grep/Read + CLAUDE.md = hybrid retrieval.

**Gaps**
- The post does not give the compaction prompt or thresholds used in Claude Code.

### Q5. Tool design: "Writing effective tools for agents — with agents" (Sep 11, 2025) and "Code execution with MCP" (Nov 4, 2025)

**Takeaway**
Tools are "a contract between deterministic systems and non-deterministic agents": build few, consolidated, namespaced tools that return high-signal, token-efficient results, write descriptions as for a new hire, and iterate with evals and with Claude itself. When tool catalogs or intermediate results get large, present tools as code APIs the agent calls from a sandbox; Anthropic reports a 150,000 → 2,000 token reduction (98.7%) for one workflow.

**Cited Findings**
- Development loop: prototype (local MCP server or DXT; give Claude Code `llms.txt`); evaluate with realistic multi-step tasks in a simple while-loop agent, tracking accuracy, runtime, tool calls, token use, errors; analyze transcripts and paste them into Claude Code to refactor tools; use held-out sets. — [Writing effective tools for agents, official blog, 2025-09-11](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Principles: "More tools don't always lead to better outcomes" — consolidate (`schedule_event` instead of list + create); namespace by service/resource (`asana_search`, `asana_projects_search`; prefix vs suffix matters per model); return meaningful context (`name` over `uuid`; resolving UUIDs to names "improved retrieval precision by reducing hallucinations"; a `response_format` enum DETAILED/CONCISE); token efficiency via pagination, filtering, truncation, 25k default cap; descriptions "as you would to a new hire", unambiguous params (`user_id` not `user`). — [same](https://www.anthropic.com/engineering/writing-tools-for-agents)
- Numbers: detailed Slack-style response ≈206 tokens vs concise ≈72 (about one third); Claude Sonnet 3.5 reached SOTA on SWE-bench Verified after tool-description refinements; the web search tool was appending "2025" to queries until its description was fixed. "Even small refinements to tool descriptions can yield dramatic improvements." — [same](https://www.anthropic.com/engineering/writing-tools-for-agents)
- MCP code execution: problems are tool definitions crowding context ("Tool descriptions occupy more context window space, increasing response time and costs") and intermediate results flowing through the model ("For a 2-hour sales meeting, that could mean processing an additional 50,000 tokens"). Solution: each tool is a file like `servers/google-drive/getDocument.ts`; the agent lists directories and reads only what it needs, then writes code. — [Code execution with MCP, official blog, 2025-11-04](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Headline: "reduces the token usage from 150,000 tokens to 2,000 tokens", a 98.7% reduction. — [same](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Benefits: progressive disclosure (or a `search_tools` tool); context-efficient results (five rows instead of 10,000); control flow as code; privacy (PII tokenized by the MCP client); state persistence and reusable functions that become skills with a SKILL.md. Caveat: "Running agent-generated code requires a secure execution environment with appropriate sandboxing." — [same](https://www.anthropic.com/engineering/code-execution-with-mcp)
- Multi-agent research post numbers on tools: rewriting tool descriptions gave "a 40% decrease in task completion time"; Claude 4 models can "diagnose failures and rewrite tool descriptions". — [How we built our multi-agent research system, official blog, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system)
- Product follow-through: Claude Code's `ToolSearch` tool and deferred MCP schemas (Q1) implement the progressive-disclosure idea; the engineering index also lists "Introducing advanced tool use on the Claude Developer Platform" (2025-11-24), not fetched. — [Engineering index](https://www.anthropic.com/engineering)

**Inferences**
- The three tool posts (Dec 2024 ACI appendix, Sep 2025 tools post, Nov 2025 MCP code-exec post) form a progression: fix argument shapes → fix descriptions and return payloads → move the whole catalog out of the prompt.

**Gaps**

### Q6. Evaluating harnesses ("Demystifying evals", Jan 9, 2026), "How Anthropic teams use Claude Code" (Jul 24, 2025), and Claude Code best practices (Apr 18, 2025 → living docs page)

**Takeaway**
Evals: start with 20–50 tasks from real failures, grade outcomes not paths, prefer deterministic graders, read transcripts, watch for saturation and for the harness constraining the model. Best practices: give Claude a check it can run, explore→plan→code→commit, keep CLAUDE.md short, use hooks for must-happen actions, subagents for investigation, `/clear` after two failed corrections, fresh-context adversarial review before calling work done.

**Cited Findings**

*Evals*
- Anatomy: task, trial, grader, transcript, outcome ("whether a reservation exists in a database, not whether the agent claimed it was booked"), evaluation harness, agent harness, suite. — [Demystifying evals for AI agents, official blog, 2026-01-09](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Grader types: code-based (fast, objective, brittle), model-based (flexible, non-deterministic, needs calibration), human (gold standard, slow). Capability evals start low; regression evals sit near 100%. — [same](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- pass@k vs pass^k: 75% per-trial over 3 trials → pass^3 ≈ 42%; by k=10 pass@k nears 100% while pass^k nears 0%. — [same](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Roadmap: "20-50 simple tasks drawn from real failures is a great start"; a good task is one where two experts reach the same verdict; balance should/shouldn't cases; clean state per trial; prefer deterministic graders, "Grade the outcome rather than the exact path", give LLM judges an "Unknown" option; read transcripts; watch saturation. — [same](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Pitfalls with numbers: Opus 4.5 scored 42% on CORE-Bench, 95% after fixing grading/spec issues and "using a less constrained scaffold"; in some evals Claude read git history from previous trials, inflating results; grading "96.12" wrong when "96.124991…" expected. — [same](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Multi-agent research post eval guidance: "Start evaluating immediately with small samples" (~20 queries); LLM-as-judge with a single 0.0–1.0 rubric plus pass/fail matched humans best; for state-changing agents "evaluate whether it achieved the correct final state". — [Multi-agent research system, official blog, 2025-06-13](https://www.anthropic.com/engineering/multi-agent-research-system)
- Related 2026 posts on the index (not fetched): "Quantifying infrastructure noise in agentic coding evals" (2026-02-05), "Eval awareness in Claude Opus 4.6's BrowseComp performance" (2026-03-06), "Designing AI-resistant technical evaluations" (2026-01-21). — [Engineering index](https://www.anthropic.com/engineering)

*Best practices (actionable rules)*
- Governing constraint: "Most best practices are based on one constraint: Claude's context window fills up fast, and performance degrades as it fills." — [Best practices, official docs, fetched 2026-10-25](https://code.claude.com/docs/en/best-practices) (the April 18, 2025 engineering post "Claude Code: Best practices for agentic coding" now 308-redirects here; the page is undated and has been substantially updated)
- Verification first: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available". Four gating levels: in-prompt check; `/goal` condition re-checked by a separate evaluator each turn; a Stop hook as "a deterministic gate"; a verification subagent so "the agent doing the work isn't the one grading it". "Have Claude show evidence rather than asserting success". — [Best practices](https://code.claude.com/docs/en/best-practices)
- Explore → Plan → Implement → Commit using plan mode; "If you could describe the diff in one sentence, skip the plan." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Prompt specificity table (scope the task, point to sources, reference existing patterns, describe the symptom); use `@file`, images, URLs (allowlist domains via `/permissions`), piping (`cat error.log | claude -p`). — [Best practices](https://code.claude.com/docs/en/best-practices)
- Environment: `/init` then prune CLAUDE.md; "If you emphasize many lines, none of them stands out"; permissions via `/permissions` and `/sandbox`; prefer CLI tools (`gh`, `aws`, `gcloud`) as "the most context-efficient way to interact with external services"; hooks "for actions that must happen every time with zero exceptions"; skills in `.claude/skills/`; subagents in `.claude/agents/`; plugins via `/plugin`. — [Best practices](https://code.claude.com/docs/en/best-practices)
- Session hygiene: `Esc` to stop, `Esc Esc` / `/rewind` to restore, `/clear` between tasks; "After two failed corrections, /clear and write a better initial prompt". — [Best practices](https://code.claude.com/docs/en/best-practices)
- Scale: `claude -p` with `--output-format json|stream-json`; fan-out loop with `--allowedTools "Edit,Bash(git commit *)" --permission-mode dontAsk`; Writer/Reviewer two-session pattern ("A fresh context improves code review since Claude won't be biased toward code it just wrote"); adversarial review subagent told to "Report gaps, not style preferences" and warned that "A reviewer prompted to find gaps will usually report some". — [Best practices](https://code.claude.com/docs/en/best-practices)
- Named failure patterns: kitchen sink session, correcting over and over, over-specified CLAUDE.md, trust-then-verify gap ("If you can't verify it, don't ship it"), infinite exploration. — [Best practices](https://code.claude.com/docs/en/best-practices)
- Spec-first for big features: have Claude interview you with `AskUserQuestion`, write `SPEC.md`, then "start a fresh session to execute it." — [Best practices](https://code.claude.com/docs/en/best-practices)

- Event: a ~59.8 MB debug source map shipped in npm `@anthropic-ai/claude-code` 2.1.88; roughly 1,900 TypeScript files and ~512,000 lines; found by researcher Chaofan Shou; Anthropic described it as a packaging error with no customer data exposed. — [Varonis Threat Labs, third party, updated 2026-04-03](https://www.varonis.com/blog/claude-code-leak); corroborated by [Help Net Security, third party, 2026-04-03](https://www.helpnetsecurity.com/2026/04/03/claude-code-leak-github-malware/) and [heise, third party](https://www.heise.de/en/news/Claude-Code-unintentionally-open-source-Source-map-reveals-all-11242079.html)
